## 1. 目的与范围

本文档描述什么，不描述什么。

## 2. 当前架构

从系统边界到具体实现，每层写出模块路径、职责的一句话描述、依赖方向和一条完整数据流链路。不要写"模块 A 负责核心逻辑"这种无信息量的句子。示例：`src/main/agent/` 接收 Renderer 经 IPC 发来的 `chat:send` 请求，调 Provider，通过受控事件流推送 delta 到 Renderer。

## 3. 核心接口

至少一条给出完整契约：名称、入参类型、出参类型和关键约束（超时、幂等、错误码）。示例：`chat:send` 入参 `{ message: string }`，返回 `requestId`，通过 `chat:stream` 事件推送 `{ requestId, text, directive }`。不要只写"API 和消息"这种概括词。

## 4. 约束与不变量

系统始终满足的硬规则，每条至少包含：触发条件、具体数值或边界、违反时的行为。示例："单个 IPC Handler 执行不超过 5 秒，超时返回 `INTERNAL_TIMEOUT`"；"禁写"Renderer 不能访问 Node API"。

## 5. 安全与失败处理

权限边界、错误分类与映射、重试策略和资源回收，每条写清"什么场景→什么错误→怎么处理"。示例："网络断开 → `NETWORK_UNAVAILABLE` → 面板显示'网络不可用，检查后重试'，不弹系统错误框"。"Renderer 崩溃 → 24h 内最多重载 2 次，超限停止并记录日志"。

## 7. 已知限制

"什么情况下会出什么问题"——不是"性能可能有问题"，而是"`idle` 状态若未清理定时器会导致内存每 30 分钟增长约 50 MB"。如果没有已知限制，写"当前无"。
