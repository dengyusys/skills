## 功能 Spec 工作流

### 何时创建 Spec

满足以下任一条件时，通常应先创建 Spec：

- 会改变用户可见行为；
- 涉及多个模块、服务或进程；
- 会新增或修改 API、消息协议、数据表或迁移；
- 存在明显的安全、权限或数据风险；
- 预计开发时间超过半天；
- 需要多人或 AI Agent 连续执行多个步骤；
- 完成标准无法用一句话清楚说明。

简单文案修改、无行为变化的样式调整和明显 Bug 修复可以不创建独立 Spec，但仍需有明确任务描述和验证结果。

### 生命周期

```text
Draft
→ Approved
→ In Progress
→ Completed
```

异常分支：

```text
In Progress → Blocked
Approved → Deprecated
Completed → Superseded
```

### 开发前

1. 阅读产品范围和相关架构；
2. 检查是否已有相同或重叠 Spec；
3. 写明背景、目标、范围和非目标；
4. 明确用户流程、技术影响和边界情况；
5. 给出可以实际判断的验收标准；
6. 状态变为 `Approved` 后再开始实施。

### 开发中

- 合理实现偏差应及时反映到 Spec；
- 重大方案变化先更新决策或架构；
- 只修改当前功能真正影响的文档；
- 范围外问题登记为后续任务，不顺手扩大实现；
- 未经验证的结果不得标记为完成。

### 开发完成后

1. 按验收标准逐项验证；
2. 记录真实测试或验证结果；
3. 确认代码、Spec 和架构一致；
4. 将 Spec 状态改为 `Completed`；
5. 更新阶段进度；
6. 如果总体范围或架构改变，同步更新上层文档。

## 文档更新规则

### 必须更新文档的变化

- 产品范围、用户流程或外部行为改变；
- API、事件、消息或 IPC 结构改变；
- 数据表、字段、文件格式或迁移改变；
- 模块职责和依赖方向改变；
- 安全策略、权限或认证方式改变；
- 配置、部署、备份或恢复流程改变；
- 原有验收标准不再适用；
- 重要技术决策被替代。

### 通常不需要更新长期文档的变化

- 变量或私有函数重命名；
- 不改变行为的内部重构；
- 格式化和注释修正；
- 测试内部结构调整；
- 无长期价值的排错过程；
- 不改变行为的补丁版本升级。

### 更新检查顺序

功能变化后按以下顺序检查：

1. 目标功能 Spec；
2. 相关架构文档；
3. 产品文档；
4. 决策记录；
5. 阶段进度；
6. README、运维文档或 Agent 规则。

不是每次变化都要修改全部文件，只更新真正受到影响的文档。

### 文档更新必须与代码同批完成

如果代码变更导致现有文档失效，文档更新应包含在同一个任务、提交或 Pull Request 中，避免长期存在“代码已更新，文档以后再补”的状态。

## 信息来源与冲突处理

### 信息优先级

不同问题应使用不同的主要依据：

| 问题 | 主要依据 |
| --- | --- |
| 产品当前做不做 | Active 产品文档 |
| 系统当前如何运行 | 代码、测试和 Active 架构文档 |
| 某功能如何验收 | Approved 或 In Progress 功能 Spec |
| 为什么选择某方案 | Accepted 决策记录 |
| 当前做到哪里 | 阶段进度或任务系统 |
| 如何部署和恢复 | Active 运维文档 |
| 自动化工具如何操作仓库 | AGENTS.md 或对应规则文件 |

### 冲突处理流程

1. 标记发生冲突的内容；
2. 查阅相关代码、测试、决策和提交历史；
3. 确认当前真实意图；
4. 修正过期文档或错误实现；
5. 必要时新增决策记录；
6. 确保最终只有一个当前有效结论。

### 不确定时的处理

如果冲突会影响数据、安全、外部接口或大范围代码，不应自行假设。应暂停相关修改并向负责人确认。

## 归档、替代与删除

### 应保留的历史

- 已指导重要版本开发的 Spec；
- 记录长期技术选择的决策；
- 对理解数据迁移和兼容性仍有价值的文档；
- 被新方案替代但仍需追溯的设计。

这些文档应标记为 `Superseded` 或 `Archived`，并指出替代文档。

### 可以删除的内容

- 空文件；
- 重复且未被引用的草稿；
- 无结论、无引用的临时记录；
- 已完整合并进正式文档且无独立价值的副本；
- 自动生成且可随时重新生成的临时文档。

删除前检查其他文档是否引用。重要历史由 Git 保留，不创建大量“备份版”“旧版”“最终版”文件。

### archive 目录

只有需要在当前工作区继续直接查阅的历史资料才进入 `archive/`。一般过期内容优先通过 Git 历史查询，避免归档目录无限增长。
