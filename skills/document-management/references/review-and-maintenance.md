## AI Agent 协作规则

使用 AI Agent 辅助开发时，应将文档作为上下文和约束系统，而不是一次性提示词。

### 开发前

AI Agent 应：

1. 阅读仓库级规则；
2. 阅读文档索引；
3. 阅读相关产品范围、目标 Spec 和架构文档；
4. 检查目标 Spec 的状态和非目标；
5. 检查是否存在相关决策记录；
6. 发现冲突或重大缺失时先报告，不自行补全关键决策。

### 开发中

AI Agent 不得：

- 未经确认改变产品定位和阶段范围；
- 为追求架构完整擅自引入大型依赖或新平台；
- 同时创建多份内容重复的方案文档；
- 用新文件替代现有有效文档而不说明关系；
- 发现代码和文档不一致后静默选择一方；
- 把范围外问题顺带实现；
- 将真实密钥、Token、个人敏感数据或完整生产日志写入文档。

### 开发后

AI Agent 应：

1. 按验收标准执行真实验证；
2. 区分“已验证”“未验证”和“无法验证”；
3. 更新目标 Spec 的实施结果和状态；
4. 更新受影响的架构或运维文档；
5. 更新阶段进度；
6. 不把未经执行的测试描述为已通过；
7. 不把大量临时输出复制进长期文档。

### 推荐阅读顺序

```text
仓库级规则
→ docs/README.md
→ 产品范围
→ 当前阶段进度
→ 目标功能 Spec
→ 相关架构文档
→ 相关决策和运维文档
```

上下文有限时，优先读取目标 Spec、相关架构、当前范围和安全约束。

## 文档评审标准

一份可以指导实施的文档应满足：

- 目标和范围明确；
- 明确说明非目标；
- 使用稳定、统一的术语；
- 关键结论可以定位；
- 不包含相互冲突的当前方案；
- 验收标准可观察、可验证；
- 关键约束包含有可靠依据的具体数值、文件路径或可验证方法，不出现无法判断的表述（如“确保性能可接受”“保持代码整洁”）；
- 风险、权限和异常边界得到说明；
- 链接和引用指向当前有效文档；
- 不包含密钥和敏感信息；
- 内容与当前代码或计划一致。

文档不需要追求文学性，优先保证准确、简洁、可执行和可维护。

## 维护节奏

### 每次功能开发前

- 确认或创建功能 Spec；
- 检查当前产品范围；
- 阅读相关架构和决策；
- 明确验收标准。

### 每次功能完成后

- 更新 Spec 状态和实施结果；
- 更新阶段进度；
- 检查架构、接口和运维文档是否受影响；
- 删除无价值的临时文档。

### 每个里程碑结束时

- 检查所有 `In Progress` 和 `Blocked` 文档是否真实；
- 清理重复或过期草稿；
- 检查产品、架构和代码是否存在重大偏差；
- 汇总未完成内容到下一阶段；
- 为重要新选择补充决策记录。

### 每次发布前

- 确认发布范围内 Spec 已验收；
- 更新安装、配置、部署和回滚说明；
- 检查数据迁移和兼容性文档；
- 更新用户可见的变更记录；
- 检查文档中是否包含密钥和敏感数据。

### 定期治理

长期项目可以每月或每个大版本进行一次文档治理：

- 检查失效链接；
- 检查长时间未更新的 Active 文档；
- 检查重复主题；
- 检查已经被代码推翻的旧结论；
- 检查是否存在无人维护的 Draft；
- 对过长文档进行合理拆分。

## 新项目落地顺序

新项目不需要立即建立完整文档体系，建议按以下顺序逐步增加：

1. 根目录 `README.md`：项目目的和运行方式；
2. `docs/product.md`：范围、目标和非目标；
3. `docs/architecture.md`：初始模块和数据流；
4. `docs/progress.md`：当前计划和状态；
5. 为第一个复杂功能创建 `docs/specs/001-*.md`；
6. 出现重要技术选择时创建第一份决策记录；
7. 出现部署和长期运行需求时创建运维文档；
8. 文件增多后创建 `docs/README.md` 并拆分目录。

这套顺序可以让文档随着实际复杂度增长，避免项目尚未开始就产生大量推测性设计。

## 完成标准

当本规范应用到一个项目后，应达到以下结果：

- 新成员可以通过 README 和文档索引快速理解项目；
- 每个复杂功能都有明确范围和验收标准；
- 当前架构与代码基本一致；
- 重要技术选择能够追溯原因；
- 当前进度和阻塞项可以快速确认；
- 旧方案不会与当前方案混淆；
- AI Agent 能够找到足够上下文，但不会被大量过期信息误导；
- 文档更新成为开发完成条件的一部分，而不是额外善后工作。
