# 软件项目通用文档管理规范

> 文档版本：v1.0  
> 状态：Active  
> 适用范围：由个人或团队维护的软件项目，包括使用 AI Agent 辅助开发的项目

---

## 1. 文档目的

本规范用于管理软件项目在产品设计、架构设计、功能开发、测试、发布和维护过程中产生的文档，确保开发者、维护者和 AI Agent 能够快速判断：

- 项目为什么存在、当前要做什么；
- 系统实际上如何工作；
- 某项功能为什么采用当前方案；
- 某个功能是否已经完成并通过验收；
- 哪份文档是当前有效依据；
- 需求、设计、代码和进度不一致时如何处理。

本规范不限定具体编程语言、框架、平台或业务领域，可以作为新项目的基础文档模板，也可以逐步引入已有项目。

---

## 2. 核心原则

### 2.1 一类文档只解决一类问题

- 产品文档回答“为什么做、为谁做、做什么”；
- 架构文档回答“系统整体如何实现”；
- 功能 Spec 回答“具体功能如何开发和验收”；
- 决策记录回答“为什么选择这个方案”；
- 进度文档回答“目前做到哪里、下一步是什么”；
- 运维文档回答“如何部署、运行、监控和恢复”。

不要把产品规划、代码细节、排错记录、会议纪要和每日进度堆在同一个文件中。

### 2.2 文档是持续维护的项目资产

文档不是开发前生成一次、开发后丢弃的材料。产品范围、系统行为、接口、数据结构或重要决策发生变化后，受影响的文档应与代码同步更新。

### 2.3 代码描述事实，文档解释意图

代码和运行结果是系统行为的最终事实来源；文档负责说明目标、设计意图、约束、边界、使用方式和决策原因。

当代码与文档不一致时：

1. 如果代码偏离已确认需求，应修正代码；
2. 如果实施证明原方案不可行，应更新设计或决策，再保留正确实现；
3. 如果无法判断哪一方正确，应暂停相关扩展，先确认差异；
4. 不允许静默选择一方并继续扩大修改范围。

### 2.4 文档数量服从项目复杂度

文档越多不代表管理越好。小项目使用少量核心文档即可；只有出现真实的信息分层和协作需求时，才增加目录和文件。

### 2.5 保留有效历史，不保留过程噪声

重要决策、已完成 Spec、迁移说明和发布记录应保留。临时命令输出、重复排错过程、无结论草稿和可从 Git 直接恢复的副本不进入长期文档。

### 2.6 一个主题只有一个当前有效来源

同一主题不能长期存在两份都声称有效、但内容不同的文档。旧方案应明确标记为已替代或归档，并链接到新方案。

### 2.7 文档内容具体可验证

文档应能指导实施和判断，不堆砌抽象概念。必须避免以下三类反模式：

**(1) 过于概括的管理式陈述**

反面示例：
> 功能行为符合产品文档和对应 Spec。

正面示例：
> 对照 Spec 的验收标准清单，逐条在真机上操作并确认通过。故意触发一个失败路径（错误 Key、空输入、断网），确认应用给出脱敏提示且不崩溃。

反面示例：
> 严格执行产品非目标与里程碑验收。

正面示例：
> 发现额外需求时，先在 Spec 的"非目标"栏目记录并标注"后续评估"。如果确实影响当前功能正确性且无法绕开，更新 Spec 和产品文档后再实现。

**(2) 缺少具体值的软约束**

反面示例：
> Renderer 崩溃后允许有限次数重载。初始化日志、存储和 Repository。

正面示例：
> Renderer 崩溃后最多自动重载 2 次，24 小时内超过 2 次则停止重载并记录错误日志。`src/main/logging/` 初始化文件日志（写入 `userData/logs/`），`src/main/storage/` 初始化各 Repository。

每条约束必须包含至少一项：具体数值、文件路径、函数名、命令或检查方法。

**(3) 脱离业务的概念列表**

反面示例：
> 1. 安全和行为边界；2. 宠物固定人格；3. 用户基础资料。

正面示例：
> 1. 安全边界（告诉模型不能执行终端命令、访问文件系统）；2. 宠物人格（定义角色名字、性格和表达方式，如"你叫小爪，性格乐观好奇，表达像朋友闲聊"）；3. 用户资料（从 profile 记忆中取：用户称呼、职业、偏好）。

每个概念必须说清"包含什么内容"以及"与相邻概念的区别"。相邻概念之间如果分不清，就应该合并。

## 3. 推荐目录结构

### 3.1 标准结构

```text
docs/
├── README.md
├── product/
│   ├── product-overview.md
│   └── roadmap.md
├── architecture/
│   ├── system-overview.md
│   ├── module-design.md
│   ├── api-design.md
│   └── data-design.md
├── specs/
│   ├── 001-project-initialization.md
│   ├── 002-feature-name.md
│   └── 003-another-feature.md
├── decisions/
│   ├── 001-technology-choice.md
│   └── 002-architecture-change.md
├── progress/
│   ├── phase-1.md
│   └── phase-2.md
├── operations/
│   ├── deployment.md
│   ├── configuration.md
│   └── troubleshooting.md
└── archive/
```

项目根目录通常保留：

```text
README.md
AGENTS.md
CONTRIBUTING.md
CHANGELOG.md
```

- `README.md`：项目介绍、快速开始和常用命令；
- `AGENTS.md`：AI Agent 或自动化开发工具的仓库级规则，可选；
- `CONTRIBUTING.md`：人工协作、分支、提交和评审规范，可选；
- `CHANGELOG.md`：对外发布版本的用户可见变化，可选。

### 3.2 小型项目最小结构

个人项目或早期原型可以从以下结构开始：

```text
docs/
├── product.md
├── architecture.md
├── specs/
└── progress.md
```

当单个文件明显过长、多人协作频繁或模块边界稳定后，再拆分为标准结构。

### 3.3 创建原则

- 不一次性创建大量空文件；
- 文档在对应需求真实出现时创建；
- 目录服务于检索，不追求形式完整；
- 同一主题已有文档时优先更新，不重复创建；
- 临时研究内容只有形成结论后才进入正式文档。

## 4. 文档类型与职责

| 类型 | 推荐目录 | 生命周期 | 主要内容 |
| --- | --- | --- | --- |
| 项目入口 | 根目录、`docs/README.md` | 长期维护 | 项目介绍、文档索引、阅读顺序 |
| 产品文档 | `docs/product/` | 长期维护 | 定位、用户、范围、优先级、路线图 |
| 架构文档 | `docs/architecture/` | 长期维护 | 模块、接口、数据、部署、安全边界 |
| 功能 Spec | `docs/specs/` | 功能全生命周期 | 单项功能需求、方案、任务和验收 |
| 决策记录 | `docs/decisions/` | 永久保留 | 重要选择、替代方案、收益与代价 |
| 阶段进度 | `docs/progress/` | 阶段内维护 | 已完成、进行中、下一步和阻塞项 |
| 运维文档 | `docs/operations/` | 长期维护 | 配置、部署、监控、备份和恢复 |
| 归档文档 | `docs/archive/` | 只读保留 | 已被替代但仍有历史价值的内容 |

### 4.1 项目入口文档

根目录 `README.md` 面向首次接触项目的人，应该保持简洁，通常包含：

- 项目用途；
- 当前状态；
- 环境要求；
- 安装和启动命令；
- 测试和构建命令；
- 文档入口；
- 许可证或协作方式。

`docs/README.md` 作为文档索引，列出当前有效文档、状态和推荐阅读顺序。

### 4.2 产品文档

产品文档只描述稳定的产品信息：

- 问题与目标用户；
- 产品定位和核心价值；
- 当前范围与明确非目标；
- 主要用户流程；
- 功能优先级；
- 阶段计划与成功标准。

产品文档不记录组件代码、具体函数、临时排错和每日进度。

### 4.3 架构文档

架构文档描述当前系统实际采用的结构：

- 系统上下文和模块边界；
- 依赖方向和数据流；
- API、消息或进程通信；
- 数据模型、存储和迁移；
- 认证、权限和安全策略；
- 错误、日志、监控和资源管理；
- 部署拓扑和运行环境。

架构文档以当前有效方案为主。被替代方案通过决策记录或 Git 历史查询，不在正文中长期并列多套冲突方案。

每个设计点应写出具体方案，而不只是概念名称——例如不写"模块 A 负责核心逻辑"，而写"`src/main/agent/` 接收 `chat:send`，调 Provider，推流式事件回 Renderer"。

### 4.4 功能 Spec

一个 Spec 负责一个可以独立开发和验收的功能，或一组不可拆分的紧密功能。

适合独立建立 Spec 的例子：

- 用户登录；
- 文件上传；
- 消息通知；
- 数据导出；
- 缓存策略；
- 数据库迁移；
- 权限控制。

不要建立“完成整个系统”这种过大的 Spec，也不要为不影响行为的简单样式调整创建独立 Spec。

### 4.5 决策记录

决策记录采用简化 ADR 形式，适用于：

- 选择语言、框架、数据库或基础设施；
- 选择模块划分和通信方式；
- 引入或移除关键依赖；
- 改变数据模型、部署方式或安全边界；
- 在多个合理方案中作出影响长期维护的选择。

已经采纳的决策即使后来被替代也不删除，应标记为 `Superseded` 并链接到新决策。

### 4.6 阶段进度

阶段进度只记录当前执行状态：

- 当前阶段目标；
- 已完成；
- 进行中；
- 下一步；
- 阻塞项；
- 最近验证结果。

阶段进度不是流水账。已经解决且没有长期价值的问题，应从正文移除或压缩为结论。

### 4.7 运维文档

当项目存在部署或长期运行需求时，运维文档至少覆盖：

- 环境变量和配置来源；
- 部署、升级和回滚；
- 数据备份与恢复；
- 日志和监控入口；
- 常见故障及安全处理方式；
- 密钥管理原则，但不记录真实密钥。

## 5. 命名规则

### 5.1 通用规则

- 文件名使用小写英文和短横线；
- Markdown 文件统一使用 `.md`；
- 文件名表达主题，不使用 `new`、`final`、`latest`、`最新版`；
- 版本变化通过 Git 和文档元信息管理，不复制多个版本文件；
- 正文可使用项目主要语言，代码标识符保持原始形式。

推荐：

```text
product-overview.md
api-design.md
data-export.md
```

不推荐：

```text
新建文档.md
最终版开发方案.md
接口设计最新版-v3.md
```

### 5.2 Spec 编号

功能 Spec 使用三位递增编号：

```text
001-project-initialization.md
002-user-authentication.md
003-data-export.md
```

编号表示创建顺序，不表示优先级。文档废弃后不复用编号。

### 5.3 决策编号

决策记录单独编号：

```text
001-use-postgresql.md
002-adopt-event-driven-processing.md
```

Spec 和决策记录分别编号，互不关联。

## 6. 文档元信息与状态

### 6.1 推荐格式

产品、架构、Spec、决策和运维文档应在标题后提供简短元信息：

```md
> 状态：Draft  
> 创建日期：YYYY-MM-DD  
> 最后更新：YYYY-MM-DD  
> 负责人：姓名或团队  
> 关联里程碑：可选  
> 关联模块：module-name
```

个人项目可以省略负责人。已经使用 Git 管理时，不需要在正文维护完整修改历史。

### 6.2 通用状态

| 状态 | 含义 |
| --- | --- |
| `Draft` | 正在讨论，不能直接作为实施依据 |
| `Approved` | 已确认，可以开始实施 |
| `In Progress` | 正在实施 |
| `Completed` | 已实现并通过验收 |
| `Blocked` | 存在阻塞，暂时无法继续 |
| `Active` | 当前持续有效并长期维护 |
| `Deprecated` | 不再推荐使用，但暂时保留 |
| `Superseded` | 已被另一文档或决策替代 |
| `Archived` | 已归档，不再维护 |

### 6.3 决策状态

决策记录通常使用：

- `Proposed`：等待确认；
- `Accepted`：已采纳；
- `Rejected`：未采纳；
- `Superseded`：已被新决策替代。

## 7. 功能 Spec 工作流

### 7.1 何时创建 Spec

满足以下任一条件时，通常应先创建 Spec：

- 会改变用户可见行为；
- 涉及多个模块、服务或进程；
- 会新增或修改 API、消息协议、数据表或迁移；
- 存在明显的安全、权限或数据风险；
- 预计开发时间超过半天；
- 需要多人或 AI Agent 连续执行多个步骤；
- 完成标准无法用一句话清楚说明。

简单文案修改、无行为变化的样式调整和明显 Bug 修复可以不创建独立 Spec，但仍需有明确任务描述和验证结果。

### 7.2 生命周期

```text
Draft
→ Approved
→ In Progress
→ Completed
```

异常分支：

```text
In Progress → Blocked
Approved → Deprecated
Completed → Superseded
```

### 7.3 开发前

1. 阅读产品范围和相关架构；
2. 检查是否已有相同或重叠 Spec；
3. 写明背景、目标、范围和非目标；
4. 明确用户流程、技术影响和边界情况；
5. 给出可以实际判断的验收标准；
6. 状态变为 `Approved` 后再开始实施。

### 7.4 开发中

- 合理实现偏差应及时反映到 Spec；
- 重大方案变化先更新决策或架构；
- 只修改当前功能真正影响的文档；
- 范围外问题登记为后续任务，不顺手扩大实现；
- 未经验证的结果不得标记为完成。

### 7.5 开发完成后

1. 按验收标准逐项验证；
2. 记录真实测试或验证结果；
3. 确认代码、Spec 和架构一致；
4. 将 Spec 状态改为 `Completed`；
5. 更新阶段进度；
6. 如果总体范围或架构改变，同步更新上层文档。

## 8. 文档更新规则

### 8.1 必须更新文档的变化

- 产品范围、用户流程或外部行为改变；
- API、事件、消息或 IPC 结构改变；
- 数据表、字段、文件格式或迁移改变；
- 模块职责和依赖方向改变；
- 安全策略、权限或认证方式改变；
- 配置、部署、备份或恢复流程改变；
- 原有验收标准不再适用；
- 重要技术决策被替代。

### 8.2 通常不需要更新长期文档的变化

- 变量或私有函数重命名；
- 不改变行为的内部重构；
- 格式化和注释修正；
- 测试内部结构调整；
- 无长期价值的排错过程；
- 不改变行为的补丁版本升级。

### 8.3 更新检查顺序

功能变化后按以下顺序检查：

1. 目标功能 Spec；
2. 相关架构文档；
3. 产品文档；
4. 决策记录；
5. 阶段进度；
6. README、运维文档或 Agent 规则。

不是每次变化都要修改全部文件，只更新真正受到影响的文档。

### 8.4 文档更新必须与代码同批完成

如果代码变更导致现有文档失效，文档更新应包含在同一个任务、提交或 Pull Request 中，避免长期存在“代码已更新，文档以后再补”的状态。

## 9. 信息来源与冲突处理

### 9.1 信息优先级

不同问题应使用不同的主要依据：

| 问题 | 主要依据 |
| --- | --- |
| 产品当前做不做 | Active 产品文档 |
| 系统当前如何运行 | 代码、测试和 Active 架构文档 |
| 某功能如何验收 | Approved 或 In Progress 功能 Spec |
| 为什么选择某方案 | Accepted 决策记录 |
| 当前做到哪里 | 阶段进度或任务系统 |
| 如何部署和恢复 | Active 运维文档 |
| 自动化工具如何操作仓库 | AGENTS.md 或对应规则文件 |

### 9.2 冲突处理流程

1. 标记发生冲突的内容；
2. 查阅相关代码、测试、决策和提交历史；
3. 确认当前真实意图；
4. 修正过期文档或错误实现；
5. 必要时新增决策记录；
6. 确保最终只有一个当前有效结论。

### 9.3 不确定时的处理

如果冲突会影响数据、安全、外部接口或大范围代码，不应自行假设。应暂停相关修改并向负责人确认。

## 10. 归档、替代与删除

### 10.1 应保留的历史

- 已指导重要版本开发的 Spec；
- 记录长期技术选择的决策；
- 对理解数据迁移和兼容性仍有价值的文档；
- 被新方案替代但仍需追溯的设计。

这些文档应标记为 `Superseded` 或 `Archived`，并指出替代文档。

### 10.2 可以删除的内容

- 空文件；
- 重复且未被引用的草稿；
- 无结论、无引用的临时记录；
- 已完整合并进正式文档且无独立价值的副本；
- 自动生成且可随时重新生成的临时文档。

删除前检查其他文档是否引用。重要历史由 Git 保留，不创建大量“备份版”“旧版”“最终版”文件。

### 10.3 archive 目录

只有需要在当前工作区继续直接查阅的历史资料才进入 `archive/`。一般过期内容优先通过 Git 历史查询，避免归档目录无限增长。

## 11. AI Agent 协作规则

使用 AI Agent 辅助开发时，应将文档作为上下文和约束系统，而不是一次性提示词。

### 11.1 开发前

AI Agent 应：

1. 阅读仓库级规则；
2. 阅读文档索引；
3. 阅读相关产品范围、目标 Spec 和架构文档；
4. 检查目标 Spec 的状态和非目标；
5. 检查是否存在相关决策记录；
6. 发现冲突或重大缺失时先报告，不自行补全关键决策。

### 11.2 开发中

AI Agent 不得：

- 未经确认改变产品定位和阶段范围；
- 为追求架构完整擅自引入大型依赖或新平台；
- 同时创建多份内容重复的方案文档；
- 用新文件替代现有有效文档而不说明关系；
- 发现代码和文档不一致后静默选择一方；
- 把范围外问题顺带实现；
- 将真实密钥、Token、个人敏感数据或完整生产日志写入文档。

### 11.3 开发后

AI Agent 应：

1. 按验收标准执行真实验证；
2. 区分“已验证”“未验证”和“无法验证”；
3. 更新目标 Spec 的实施结果和状态；
4. 更新受影响的架构或运维文档；
5. 更新阶段进度；
6. 不把未经执行的测试描述为已通过；
7. 不把大量临时输出复制进长期文档。

### 11.4 推荐阅读顺序

```text
仓库级规则
→ docs/README.md
→ 产品范围
→ 当前阶段进度
→ 目标功能 Spec
→ 相关架构文档
→ 相关决策和运维文档
```

上下文有限时，优先读取目标 Spec、相关架构、当前范围和安全约束。

## 12. 文档评审标准

一份可以指导实施的文档应满足：

- 目标和范围明确；
- 明确说明非目标；
- 使用稳定、统一的术语；
- 关键结论可以定位；
- 不包含相互冲突的当前方案；
- 验收标准可观察、可验证；
- 关键约束包含具体数值、文件路径或可验证方法，不出现无法判断的表述（如"确保性能可接受""保持代码整洁"）；
- 风险、权限和异常边界得到说明；
- 链接和引用指向当前有效文档；
- 不包含密钥和敏感信息；
- 内容与当前代码或计划一致。

文档不需要追求文学性，优先保证准确、简洁、可执行和可维护。

## 14. 维护节奏

### 每次功能开发前

- 确认或创建功能 Spec；
- 检查当前产品范围；
- 阅读相关架构和决策；
- 明确验收标准。

### 每次功能完成后

- 更新 Spec 状态和实施结果；
- 更新阶段进度；
- 检查架构、接口和运维文档是否受影响；
- 删除无价值的临时文档。

### 每个里程碑结束时

- 检查所有 `In Progress` 和 `Blocked` 文档是否真实；
- 清理重复或过期草稿；
- 检查产品、架构和代码是否存在重大偏差；
- 汇总未完成内容到下一阶段；
- 为重要新选择补充决策记录。

### 每次发布前

- 确认发布范围内 Spec 已验收；
- 更新安装、配置、部署和回滚说明；
- 检查数据迁移和兼容性文档；
- 更新用户可见的变更记录；
- 检查文档中是否包含密钥和敏感数据。

### 定期治理

长期项目可以每月或每个大版本进行一次文档治理：

- 检查失效链接；
- 检查长时间未更新的 Active 文档；
- 检查重复主题；
- 检查已经被代码推翻的旧结论；
- 检查是否存在无人维护的 Draft；
- 对过长文档进行合理拆分。

---

## 15. 新项目落地顺序

新项目不需要立即建立完整文档体系，建议按以下顺序逐步增加：

1. 根目录 `README.md`：项目目的和运行方式；
2. `docs/product.md`：范围、目标和非目标；
3. `docs/architecture.md`：初始模块和数据流；
4. `docs/progress.md`：当前计划和状态；
5. 为第一个复杂功能创建 `docs/specs/001-*.md`；
6. 出现重要技术选择时创建第一份决策记录；
7. 出现部署和长期运行需求时创建运维文档；
8. 文件增多后创建 `docs/README.md` 并拆分目录。

这套顺序可以让文档随着实际复杂度增长，避免项目尚未开始就产生大量推测性设计。

---

## 16. 完成标准

当本规范应用到一个项目后，应达到以下结果：

- 新成员可以通过 README 和文档索引快速理解项目；
- 每个复杂功能都有明确范围和验收标准；
- 当前架构与代码基本一致；
- 重要技术选择能够追溯原因；
- 当前进度和阻塞项可以快速确认；
- 旧方案不会与当前方案混淆；
- AI Agent 能够找到足够上下文，但不会被大量过期信息误导；
- 文档更新成为开发完成条件的一部分，而不是额外善后工作。
