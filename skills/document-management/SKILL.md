# 项目文档管理

你帮用户管一个软件项目的文档（文中例子均为示意，名字以当前项目为准）。三条总原则：

1. 别替用户做产品决定；
2. 别动用户没授权的东西；
3. 规矩打架时指出来问用户，别自己挑边。

## 拿到任务先想三件事

1. 这是什么活？五种：出主意、做评审、建文档、改文档、改完代码后的收尾。
2. 仓库里有没有现成规矩？（文档索引、产品总纲、相关的 Spec、架构或决策记录）有就照着来，只看和这活相关的部分。
3. 这个主题是不是已经有文档了？已有的话，先确认哪一份是"现在算数的"。

## 分活干

**出主意**：只给建议、清单、依赖关系、执行顺序。用户没说"建文件"，一个文件都别动。
例：用户说"帮我规划一下文档结构" → 输出一份建议清单，不创建任何文件。

**做评审**：问题按严重程度排好，标清在哪个文件哪一节。用户没说"顺手改掉"，就别改。

**建文档**：
1. 先查重：这个主题是不是已经有文档了？有 → 去改那一份，别新建。
2. 照仓库现有的目录、编号、格式来；仓库没约定，才用本技能的默认。
3. 新文档一律 `Draft` 起步；新决策记录（ADR）一律 `Proposed` 起步。

**改文档**：

先记住一句话：一个主题，从头到尾只有一份文档"现在算数"，其余都归历史。

动手前问自己两个问题。

**第一问：这次变的是什么？**（决定旧 Spec 标什么状态；两种情况都要写一篇新 ADR 讲清"为什么"）

- 整个方案不要了，换了新方案。
  例：原来把"通知"做成独立服务，现在决定并进主应用。
  → 旧 Spec 标 `Superseded`（已被替代），和新 ADR 互相留链接。
- 功能没变，只是做法变了。
  例：手写 HTTP 管道换成了现成框架（比如 Fastify），对外接口一个没动。
  → 旧 Spec 标 `Deprecated`（已过时），链接新 ADR。

**第二问：旧方案还在跑吗？**（决定删还是留；两种情况规则相同）

- 还在跑（新旧并存过渡、要留回滚窗口、数据迁移没做完）→ 文件留着、标好状态；等彻底下线了再删。
  例：合并刚上线、还要观察一周能不能回滚 → 旧 Spec 标了状态留着。
- 已经没人用了 → 可以删了（建议删，保持文档区干净；真要留也行，但状态和链接必须维护好）。
  删之前三件事：
  1. 里面**还算数的验收标准**，搬到新 Spec 或测试里；
  2. **链到它的地方**（索引、别的文档里的引用）清干净；
  3. 编号**永不复用**。

⚠️ 无论哪种情况，都不要为同一个主题再写一份新 Spec——新方案的细节写进 ADR 和架构文档就够了。
⚠️ 决策记录（ADR）永不删除：被替代的 ADR 标 `Superseded` 永久留存。

只有**功能本身变了**（做什么、做到什么算完成），才回头改 Spec 正文。

改完之后，花十秒查三个地方有没有旧内容残留：架构文档、文档索引、进度文档。

用户已经拍板的删除或移除：直接执行，不用再反复确认——照旧先搬验收标准、清引用、编号不复用。

**改完代码后的收尾**：代码改动让哪份文档的说法过时了，就更新哪份。
例：模块目录从 src/http/ 挪到了 src/modules/ → 架构文档里的旧路径要改；没提到它的文档不用动。
分寸：事实清楚的过期描述（功能已删、命令已移除、路径已变）直接修文档，不用问；只有分不清"该改代码还是该改文档"（两边意图打架）时，才停下来问。

## 红线（每条都是硬的）

- 一个主题只留一份"现在算数"的文档。
- 仓库已有约定 > 本技能的默认。
- 什么时候才建 Spec：动到用户看得见的行为、跨多个模块、动接口/数据/安全、验收标准一句话说不清。
  例：换数据库要建；修按钮错位、改文案、私有函数改名，不用建。
- 没真实验证过，不标 `Completed`；没确认是现行方案，不标 `Active` / `Accepted`。
- 代码和文档打架，还牵扯范围、数据、安全或对外接口：停下来问，别自行挑边。
- 密钥、Token、个人隐私、完整生产日志：一个字都不进文档。
- 用户没授权，不删、不归档、不改名、不批量重组文档。
- 没跑过的测试，别说跑过了。
- 没依据的数字、日期、路径、状态：宁可写"待确认"，不许编。
- 写出来的东西要能照着做、照着验。
  反例："确保性能可接受"；正例："接口 P95 < 200ms（用 test/api-benchmark.ts 实测）"。

## Reference 使用条件

按任务读取对应 reference：

| 任务 | 读取文件 |
| --- | --- |
| 理解治理原则或单一有效来源 | `references/governance-principles.md` |
| 设计文档目录、判断文档类型或职责边界 | `references/structure-and-types.md` |
| 命名、编号、元信息或状态流转 | `references/naming-and-status.md` |
| 功能 Spec 生命周期或代码配套更新 | `references/lifecycle-and-conflicts.md` |
| 判断信息来源，或处理文档与代码冲突、替代、归档或删除 | `references/lifecycle-and-conflicts.md` |
| AI Agent 文档协作或文档评审 | `references/review-and-maintenance.md` |
| 维护节奏 | `references/review-and-maintenance.md` |
| 建立完整文档体系或为新项目落地 | `references/governance-principles.md`、`references/structure-and-types.md`、`references/review-and-maintenance.md` |
| 全面审核文档体系 | 按审核范围读取上述文件；覆盖全部治理规则时读取全部 5 份 reference |

只读取与当前任务直接相关的文件。只有在用户要求建立、全面审核文档体系，或任务同时跨越多个文档类型时，才读取多份 reference；不要默认全部读取。

| 资源 | 使用场景 |

只在创建新文档时使用模板，不用模板覆盖现有文档。替换全部占位内容，并按仓库约定调整元信息。

## Scripts 使用条件

当前没有 `scripts/`，普通文档任务不需要创建或运行脚本。只有出现需要反复、确定性执行的文档校验逻辑，并且脚本已经随 Skill 提供且经过验证时，才使用脚本。

## 完工前自查

- 是出主意或评审的活：说清"我没改任何文件"。
- 是建或改文档的活：路径、命名、状态、链接、"一个主题一份有效文档"、敏感信息，逐项过一遍；Spec 还要检查有没有明确的范围、非目标、能验证的验收标准。
- 最后报告实际动了哪些文件，哪些验证过了、哪些没有。
