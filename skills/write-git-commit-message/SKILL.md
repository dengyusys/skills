# Git 提交信息

根据目标仓库自身的约定生成提交信息，不把某个仓库的语言、类型或标点格式硬编码到其他项目。

## 工作流

1. 使用 `git rev-parse --show-toplevel` 确认仓库根目录。
2. 读取仓库中的 `AGENTS.md`、`CONTRIBUTING.md`、提交规范或同类说明，找出提交语言、格式和验证要求。
3. 检查 `git status --short`、暂存区差异、工作区差异和相关未跟踪文件。存在暂存内容时，以暂存区作为本次提交的默认范围。
4. 使用 `git log -30 --no-merges --format=%s` 检查近期提交，识别语言、类型、scope、冒号后空格、大小写和正文习惯。
5. 概括本次改动的主要结果。若改动包含互不相关的多个目的，建议拆分提交。
6. 按“用户明确要求 → 仓库规则 → 稳定的近期历史 → 通用回退格式”的优先级确定写法。
7. 对照实际差异复核提交信息，避免描述未发生的改动。

若没有可提交的改动，直接说明当前没有可生成提交信息的变更，不凭空编写消息。若用户要求修改上一条提交信息，同时检查 `git show --stat --patch HEAD`，确保新消息准确覆盖该提交。

## 类型选择

优先沿用仓库已有类型。常见类型包括：

- `feat`：新增用户可见能力。
- `fix`：修复缺陷或错误行为。
- `refactor`：不改变预期行为的结构调整。
- `perf`：性能优化。
- `test`：新增或调整测试。
- `docs`：仅修改文档或注释说明。
- `build`：构建系统或依赖调整。
- `ci`：持续集成配置调整。
- `chore`：不属于以上类别的维护工作。
- `revert`：撤销已有提交。

仅当仓库历史或规范已经使用自定义类型（如 `data`）时才沿用。按主要改动意图选择类型，不按修改文件数量选择。

## 编写要求

- 描述改动带来的结果，不罗列文件名或实现步骤。
- 保持简洁、具体，使读者无需查看差异也能理解主要目的。
- 根据仓库规则和历史选择语言。
- 仅在仓库惯例明确或 scope 能有效区分模块时添加 scope。
- 严格遵循仓库现有的冒号后空格习惯；无法判断时回退为 `type: summary`。
- 标题末尾通常不加句号；只有需要解释动机、迁移方式或兼容影响时才添加正文，并在标题后留一个空行。
- 没有证据时，不添加 issue 编号、破坏性变更标记、测试结果、共同作者或签名。
- 用户指定了目标格式时，保留其大小写、空格和标点要求，除非与更高优先级的仓库规则冲突。

## 输出方式

- 用户只要求一个提交信息时，仅输出推荐结果，并使用代码格式方便复制。
- 用户要求多个方案时，最多给出三个候选，并简短说明差异。
- 用户要求校验现有提交信息时，先给出通过或不通过，再给出最小修改版本。

## 操作边界

- 默认只生成或校验提交信息，不执行 `git add`、`git commit`、`git commit --amend` 或 `git push`。
- 仅在用户明确要求执行 Git 操作时才执行相应命令。
- 实际提交前遵循仓库要求检查差异并运行必要验证；提交后核对 `HEAD` 和工作区状态。
- 除非用户明确要求推送，否则只创建本地提交。
