## 背景：为什么合并

用户点破的事实：code-reading 提示词的初衷一直是两件事——读代码讲明白 + 输出别有 AI 味（"字我都看得懂，但我完全不知道在说什么"）。此前两条线分开迭代，但实验证明它们是同一目标的两面：

1. **v6 的输出本身就是 AI 味重灾区**（从未被测过样式）：6 篇讲解合计 112 处加粗（单篇最高 33）、36 处"——"、16 处斜杠并列、6 处全角箭头。code-reading 原有断言只管内容与结构（ASCII 制表符、文字墙），样式是盲区。
2. **挂上「表达卫生预算」新标尺后**（prose_marker_budget.py，加粗≤8、——≤2、正文→=0、斜杠并列≤2）：v1-v6 全线 0-1/6（输在样式不在内容）；**v7 = v6 + 表达卫生 → 6/6 内容样式双过**。表达卫生规则可无缝移植进代码讲解。
3. **合一文本改文档不掉分**：plain-language 考卷上 v4 合一分支版 5/6，与专家版 v3（4-5/6）持平。
4. **但压缩合一不行**：v8（把 v6 蒸馏成分支塞进合一文本）跑代码考卷只有 4/6，丢分正是被蒸馏掉的 v6 细节规则（timer 跨调用存续的闭包解释、structuredClone 防缓存被改）。教训与当年 v3 压缩式 0/6 同源：规则一压缩就丢细节。

**结论：技能合一、规则不蒸馏。** 公共【表达卫生】核心 + 两个完整任务分支。

## 已知缺口（落地前修或落地后迭代）

1. **案例 05（Apple 三原则表）九轮未破**：模型不肯给表格瘦身。v8 方向：提供完整的"胖表 → 概览表 + 细节下移"改前改后整表示例。
2. **加粗遵守仍受提示词长度稀释**：07 已用严格口径，R9 仍出现加粗超标（摇摆+稀释混合）。主文件+细则结构（按需加载）本身就是缓解手段。
3. ~~代码分支的版式移植未做~~ **已解决**（v9 6/6）：版式呼吸并入代码分支可行，但表格规则必须「结构化优先 + 预算约束」，不能用「解释用短段」软化（R8 教训：Dockerfile 退化成文字堆）。
4. **预算内耗**：拆短列表项会顶爆连续列表预算（13 项 > 8），"拆完按小主题分组"的引导存在但被忽略，暂无低成本修法。
5. **约束量实验与标尺修订**（极简版 v8/v9b + glm-5.3 强模型探针 ×2 + 用户原则版 v9/v9c）：标尺经用户三次裁定逐级放宽——绝对数字预算 → 相对标记规则 → 全部形式断言观察项化（2026-09-13 终点）。文档面考卷因此饱和（50/54，基线也满分），提示词优劣的区分只剩内容级判死项（技术事实保全、不成文字墙、裁判定性）与案例专属问题。用户原则版在新尺下与 v6 平手（各 5/6），其"策略更新仅在有反馈时生成"与术语解释设计被验证为优点。极简版保留为**模型升级探针**；形式断言脚本保留在 core 随时可恢复。
