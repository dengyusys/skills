## 结论（人话版）

1. **技能值不值**：裸考 3/12，落地版 12/12。最容易犯的错（顺手再建一份重复 spec、乱删文档、没验证就标完成）都被技能防住了。
2. **为什么要大白话**：大白话完整版稳定压过原版完整版（12/12 vs 8/12），治好了原版三个老毛病（方案替代想删错文件、授权删除不敢执行、备份冲突过度保守）。要点：通俗靠**结构**（场景对号 + 例子 + 一行一事），不是把"应当"换成"要"。
3. **为什么要全套统一**：混搭（原版主文件+大白话细则）9/12，没有增益——主文件和细则语言不一致会互相稀释。
4. **已知小盲区**：主文件单独使用时，处理"被否提案"会漏提拒绝日期（其余全对，细则里有，加载后无此问题）；个别临界题两轮间会翻转（裁判波动），看模式不看单点。

## 来龙去脉（给未来的你或 AI 看，日常不用读）

**经过**：这个测试从 6 道题、3 个变体起步，前后跑了十四轮。每次改规则、改文风、加考题都重跑一遍验证。十四轮的原始分数由系统自动记在 `history.jsonl` 和 `results/` 里，这里不重复抄，只记"规则为什么是现在这样"——想动规则之前先看这份，别把老毛病改回去。

**规则修改记录**（每条写明当时出了什么问题）：

1. "别复制一份"改成"不要为同主题再开新文件"：原来那句被模型理解偏了，它以为只是别复制旧的，还是想新建一份重复的 spec。
2. "两问"结构（先问变的是什么、再问还在不在跑）：因为你审阅时发现旧规则自相矛盾——整个方案都不要了的反而留着文档，只是换了写法的反而要删。改成两个独立问题后：状态词和删留各管各的。
3. "过期描述直接修、意图冲突才问"：旧版把"文档写错了"也升级成"问用户"，模型连明摆着的过期路径都不敢改。加了分寸后治好。
4. "ADR 永不删除"、"Superseded 不是推荐删除"：都来自你审阅时的问题。删不删只看旧方案还在不在跑；ADR 例外，永不删。
5. 例子泛化：你发现例子里的"Memory 并进 Gateway"是你项目的专有名词，技能发到别的项目可能误导。改成通用角色名（"通知服务并进主应用"）后重测，成绩不掉。
6. 一次考题事故：第一轮的及格线是我闭门写的，其中案例 02 的"标准答案"和你们项目实际做法不符，那轮作废，按真实做法重新校准后一切案例冻结，此后只加不改。
