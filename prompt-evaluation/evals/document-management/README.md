# document-management：技能测试（三变体）

## 测什么

仓库 `skills/document-management` 技能的有效性。三个变体：无技能（baseline）/ 仅主文件（skill-core）/ 主文件+全部细则（skill-full）。

六案例全部取材于 D:\ai-steward-a 的 docs 真实结构与变更记录（只读摘录），覆盖技能的核心判断点：

| 案例 | 真实来源 | 考什么 |
|------|----------|--------|
| 01 方案替代 | Spec 002 被 ADR 011 替代 | spec 改还是新增（用户核心痛点）：整体方案被替代 → 新 ADR + 旧 spec 标 Superseded 双向链接 |
| 02 同主题演进 | Spec 007 + ADR 009（Fastify） | 同主题方案演进 → 直接更新原 spec，选型补 ADR |
| 03 要不要写 spec | 反向题 | 无行为变化的小改动不建 spec |
| 04 功能移除 | specs 003/006 随 Mobile 移出而删除 | 授权删除 + 索引/引用同步 + 编号不复用 |
| 05 文档代码冲突 | a6c4cd86 修正旧模块路径 | 代码为事实来源、只改受影响文档、同批提交 |
| 06 状态诚实性 | lifecycle 规则 | 未验证不得标 Completed，给正确路径 |

## 结论

1. **技能的核心红线有效**：案例 03（小改动不建 spec）、06（未验证拒标 Completed）全变体全过；案例 01 中"不要再建一份重复主题 spec"只有技能变体守住，无技能两轮都栽在"顺手再开一份新 spec"上。单一有效来源这条最容易被 AI 违反的规则，技能确实防住了。
2. **最复杂的治理判断需要完整细则**：案例 01（方案替代走 ADR + Superseded + 双向链接）只有"主文件+细则"通过——SKILL.md 主文件单独不够，Reference 按需加载是刚需（与 code-style 测试结论一致）。
3. **技能的结构性盲区（最重要发现）**：案例 02（Completed 的 spec 遇方案演进）三个变体全部失败。真实项目（ai-steward-a）的实际处置是 Spec 007 标 Deprecated + ADR 009 承载 Fastify 方案——这是"原地更新 spec / 标 Deprecated+ADR / 不动+ADR"三种自洽立场并存的高频场景，技能没有给出唯一判定规则。**"spec 到底是活文档还是历史记录"的模糊，是'反复修改 spec、不知道该改还是新增'这一使用痛点的制度根源。**
4. **技能在删除/冲突场景有过度保守倾向**：案例 04"仅主文件"反对删除已授权移除的 spec、拒绝清理索引；案例 05 技能变体把方向明确的文档过期也升级为"请求确认"，无技能反而直改。技能的"未经授权不删/冲突先确认"被泛化成"授权了也慎删、明确也先问"，付出效率代价。
5. **波及面意识全军覆没**：案例 01/02 各变体都只盯目标文档，"更新检查顺序"（架构/索引/进度）没有任何变体完整执行——细则里有这条规则但传递效果最弱。

## 建议（已于 2026-09-12 实施并回归验证）

三条改进已落进 `skills/document-management`（SKILL.md 更新小节 + lifecycle-and-conflicts.md 新增「Completed Spec 的方案演进」节），并同步镜像到本测评的技能变体。回归四轮（含一次规则精化：区分「方案被替代 → Superseded」与「同主题演进 → Deprecated/退役删除」，该区分是复测抓出的规则不精确）：

| 轮次 | 无技能 | 仅主文件 | 主文件+细则 | 说明 |
|------|:---:|:---:|:---:|------|
| 第 1 轮（校准前） | 3/6 | 2/6 | 2/6 | 断言按闭门假设，作废 |
| 第 2 轮（校准后） | 3/6 | 2/6 | 3/6 | 技能改进前的基线 |
| 第 3 轮（技能 v1 修复） | 2/6 | 5/6 | 4/6 | 授权删除/演进规则生效；但新规则没区分"替代 vs 演进"，01 偏向误删 |
| 第 4 轮（技能 v2 精化） | 3/6 | 5/6 | 4/6 | 替代走 Superseded、演进走 Deprecated/删；仅主文件 01✅02✅04✅ 全对 |

**修复效果**：仅主文件 2/6 → 5/6，案例 04（授权删除）、05（冲突，仅主文件）、02（演进，完整细则）从挂到过；无技能稳定在 2-3/6 且两轮栽在"顺手再建重复 spec"上——技能的核心增量保持。

**残留（已知，接受）**：
1. 备份/恢复类文档过期，技能变体连续三轮要求用户确认而不直接修正——对数据安全场景可辩护，但如果追求"事实清晰的过期描述直接修"，需要再加一条细化规则；
2. 案例 01 完整细则变体仍偶发首选删除（该标 Superseded 的场景），属裁判临界与难题混合，未再迭代。

## 校准记录

首轮案例 02 断言要求"直接更新 spec 正文"，与真实处置（Deprecated + ADR）不符，属断言校准错误；已按 ai-steward-a 的实际做法重写为"三种处置任一皆可，但须单一有效来源 + 状态/链接明确 + 选型记 ADR"。案例 01/04/05 的次要提醒项同步放宽为"至少覆盖一半"。校准后重跑为本 README 所载结果。
