# 项目文档管理（含全部参考细则）

## 目标

在不改变既有产品决策、仓库约定和用户授权范围的前提下，创建、更新、评审或组织软件项目文档。

## 任务入口

1. 判断任务类型：建议或规划、审核、创建、更新、代码实施后的配套文档。
2. 读取仓库级规则；若存在文档索引、产品总纲、相关 Spec、架构或决策记录，只读取与当前任务有关的内容。
3. 检查是否已有同主题文档，并确认当前有效来源。
4. 仓库规则、用户要求和当前有效文档发生冲突时，指出冲突并请求确认，不自行选择。

## 按任务执行

### 建议或规划：只输出建议、清单、依赖关系或执行顺序。用户未要求创建文件时，不修改文件。
### 审核：先输出按严重程度排序的问题，并提供文件或章节定位。用户未明确要求实施时，不修改被审核文档。
### 创建：先确认没有重复或重叠文档。遵循仓库现有目录、编号和元信息格式。新文档默认 `Draft`，新 ADR 默认 `Proposed`。
### 更新：修改当前有效文档，不另建"新版""最终版"或重复文件。确需替代时，在获得授权后标记 `Superseded`，并建立双向链接。
### 代码实施后的配套文档：只有当代码变更使现有说明失效时，才同步更新受影响文档，不扩大到无关文档。

## 核心约束

- 一个主题只保留一个当前有效来源。
- 既有仓库约定优先于本 Skill 的默认目录和命名方式。
- 涉及用户行为、多模块、接口、数据、安全风险或多步骤验收时，优先创建功能 Spec；简单文案、无行为变化的样式调整和直接 Bug 修复通常不需要。
- 未经真实验证，不得标记为 `Completed`；未确认是当前有效方案，不得标记为 `Active` 或 `Accepted`。
- 代码与文档冲突且会影响范围、数据、安全或外部接口时，暂停相关扩展并请求确认。
- 不写入真实密钥、Token、个人敏感数据或完整生产日志。
- 未经明确授权，不删除、归档、重命名或批量重组文档。
- 不把未执行的测试或检查描述为已通过。
- 不得虚构信息；缺少可靠依据时标记为"待确认""未提供"或"未验证"，并区分已确认事实、建议方案和待定项。
- 文档内容必须具体、可验证，并能明确指导操作或判断。

## 参考细则一：治理原则

- 一类文档只解决一类问题：产品文档回答"为什么做、为谁做、做什么"；架构文档回答"系统整体如何实现"；功能 Spec 回答"具体功能如何开发和验收"；决策记录回答"为什么选择这个方案"；进度文档回答"目前做到哪里"；运维文档回答"如何部署运行和恢复"。不要把产品规划、代码细节、排错记录和进度堆在同一个文件。
- 文档是持续维护的项目资产，不是开发前生成一次、开发后丢弃的材料；行为、接口、数据结构或重要决策变化后，受影响文档与代码同步更新。
- 代码描述事实，文档解释意图。代码和文档不一致时：代码偏离已确认需求则修正代码；实施证明原方案不可行则先更新设计或决策；无法判断哪一方正确则暂停扩展先确认差异；不允许静默选择一方。
- 文档数量服从项目复杂度，文档越多不代表管理越好。
- 保留有效历史，不保留过程噪声：重要决策、已完成 Spec、迁移说明保留；临时命令输出、重复排错、无结论草稿不进长期文档。
- 一个主题只有一个当前有效来源：旧方案明确标记为已替代或归档，并链接到新方案。
- 文档内容具体可验证：避免"过于概括的管理式陈述"（如"功能行为符合产品文档"）、"缺少具体值的软约束"（如"允许有限次数重载"，应写"最多自动重载 2 次"）、"脱离业务的概念列表"。每条约束至少包含一项有可靠依据的信息：具体数值、文件路径、函数名、命令或检查方法。

## 参考细则二：结构与类型

- 标准目录：docs/ 下分 README.md（索引）、product/、architecture/、specs/、decisions/、progress/、operations/、archive/。小项目可从 product.md + architecture.md + specs/ + progress.md 起步。
- 创建原则：不一次性创建大量空文件；文档在对应需求真实出现时创建；同一主题已有文档时优先更新，不重复创建；临时研究内容只有形成结论后才进入正式文档。
- 功能 Spec：一个 Spec 负责一个可独立开发和验收的功能；不要建"完成整个系统"的过大 Spec，也不为不影响行为的样式调整建 Spec。
- 决策记录（ADR）：适用于选型、模块划分、关键依赖增删、数据模型/部署/安全边界改变、多方案取舍。已采纳的决策即使后来被替代也不删除，标记 `Superseded` 并链接到新决策。
- 架构文档以当前有效方案为主，被替代方案通过决策记录或 Git 历史查询，不在正文中长期并列多套冲突方案。
- 进度文档只记录当前执行状态，不是流水账。

## 参考细则三：命名与状态

- 文件名小写英文短横线，不用 new/final/latest/最终版；版本变化通过 Git 和元信息管理，不复制多个版本文件。
- Spec 与决策各自三位递增编号（001-、002-…），编号表示创建顺序；文档废弃后不复用编号。
- 元信息：状态 / 创建日期 / 最后更新日期 / 关联模块。
- 状态集：Draft（讨论中，不能作为实施依据）、Approved（可实施）、In Progress、Completed（已实现并通过验收）、Blocked、Active（当前持续有效）、Deprecated、Superseded（已被替代）、Archived。决策记录用 Proposed/Accepted/Rejected/Superseded。

## 参考细则四：生命周期与冲突处理

### 何时创建 Spec（任一满足即建）
改变用户可见行为；涉及多模块/服务/进程；新增或修改 API、协议、数据表或迁移；有明显安全/权限/数据风险；预计开发超半天；需要多人或 Agent 连续多步骤；完成标准无法一句话说清。简单文案修改、无行为变化的样式调整和明显 Bug 修复可不建 Spec，但需有明确任务描述和验证结果。

### 生命周期
Draft → Approved → In Progress → Completed；异常分支 In Progress→Blocked、Approved→Deprecated、Completed→Superseded。开发中：合理实现偏差应及时反映到 Spec；重大方案变化先更新决策或架构；未经验证不得标完成。

### 必须更新文档的变化
产品范围/用户流程/外部行为、API 或消息结构、数据表或迁移、模块职责和依赖方向、安全策略、配置部署备份恢复流程、原有验收标准失效、重要技术决策被替代。
通常不需要更新长期文档的变化：私有重命名、不改变行为的内部重构、格式化和注释、测试内部调整、无长期价值的排错过程。

### 更新检查顺序
功能 Spec → 架构文档 → 产品文档 → 决策记录 → 阶段进度 → README/运维/Agent 规则。不是每次都改全部文件，只改真正受影响的；文档更新与代码同批提交。

### 信息优先级
产品当前做不做看 Active 产品文档；系统如何运行看代码与 Active 架构；如何验收看 Approved/In Progress Spec；为什么选某方案看 Accepted 决策记录；做到哪里看阶段进度；如何部署看 Active 运维文档。冲突时：标记冲突 → 查代码/测试/决策/提交历史 → 确认真实意图 → 修正过期方 → 必要时新增决策记录 → 最终只有一个当前有效结论。影响数据、安全、外部接口或大范围代码的冲突不自行假设，先向负责人确认。

### 归档、替代与删除
应保留：已指导重要版本的 Spec、长期技术选择决策、迁移兼容说明——标 Superseded/Archived 并指向替代文档。可以删除：空文件、重复未引用草稿、无结论临时记录、已完整合并进正式文档的副本。删除前检查其他文档引用。重要历史由 Git 保留，不创建"备份版""旧版""最终版"文件。

## 参考细则五：AI 协作与维护

### AI Agent 开发中不得
未经确认改变产品定位和阶段范围；同时创建多份内容重复的方案文档；用新文件替代现有有效文档而不说明关系；发现代码和文档不一致后静默选择一方；把范围外问题顺带实现。

### 开发后应
按验收标准真实验证；区分"已验证""未验证""无法验证"；更新 Spec 状态和实施结果；更新受影响架构/运维文档；更新阶段进度；不把未经执行的测试描述为已通过。

### 评审标准
目标范围明确、有非目标、术语统一、无相互冲突的当前方案、验收标准可观察可验证、关键约束有具体数值/路径/方法、链接指向当前有效文档、无敏感信息、与当前代码一致。

## 完成条件

建议、规划或审核任务以完成用户要求的输出为准，并明确说明未修改文件。
创建或更新任务结束前，检查目标路径、命名、元信息、状态、链接、单一有效来源和敏感信息。功能 Spec 还必须具有明确范围、非目标和可验证验收标准。
最终报告实际创建或修改的文件，并区分已验证、未验证和当前无法验证的内容。
