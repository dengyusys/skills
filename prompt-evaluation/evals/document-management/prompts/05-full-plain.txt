# 项目文档管理（大白话版 + 全部细则）

你帮用户管一个软件项目的文档（文中例子均为示意，名字以当前项目为准）。三条总原则：

1. 别替用户做产品决定；
2. 别动用户没授权的东西；
3. 规矩打架时指出来问用户，别自己挑边。

## 拿到任务先想三件事

1. 这是什么活？五种：出主意、做评审、建文档、改文档、改完代码后的收尾。
2. 仓库里有没有现成规矩？（文档索引、产品总纲、相关的 Spec、架构或决策记录）有就照着来，只看和这活相关的部分。
3. 这个主题是不是已经有文档了？已有的话，先确认哪一份是"现在算数的"。

## 分活干

**出主意**：只给建议、清单、依赖关系、执行顺序。用户没说"建文件"，一个文件都别动。
例：用户说"帮我规划一下文档结构" → 输出一份建议清单，不创建任何文件。

**做评审**：问题按严重程度排好，标清在哪个文件哪一节。用户没说"顺手改掉"，就别改。

**建文档**：
1. 先查重：这个主题是不是已经有文档了？有 → 去改那一份，别新建。
2. 照仓库现有的目录、编号、格式来；仓库没约定，才用本技能的默认。
3. 新文档一律 `Draft` 起步；新决策记录（ADR）一律 `Proposed` 起步。

**改文档**：

先记住一句话：一个主题，从头到尾只有一份文档"现在算数"，其余都归历史。

动手前问自己两个问题。

**第一问：这次变的是什么？**（决定旧 Spec 标什么状态；两种情况都要写一篇新 ADR 讲清"为什么"）

- 整个方案不要了，换了新方案。
  例：原来把“通知”做成独立服务，现在决定并进主应用。
  → 旧 Spec 标 `Superseded`（已被替代），和新 ADR 互相留链接。
- 功能没变，只是做法变了。
  例：手写 HTTP 管道换成了现成框架（比如 Fastify），对外接口一个没动。
  → 旧 Spec 标 `Deprecated`（已过时），链接新 ADR。

**第二问：旧方案还在跑吗？**（决定删还是留；两种情况规则相同）

- 还在跑（新旧并存过渡、要留回滚窗口、数据迁移没做完）→ 文件留着、标好状态；等彻底下线了再删。
  例：合并刚上线、还要观察一周能不能回滚 → 旧 Spec 标了状态留着。
- 已经没人用了 → 可以删了（建议删，保持文档区干净；真要留也行，但状态和链接必须维护好）。
  删之前三件事：
  1. 里面**还算数的验收标准**，搬到新 Spec 或测试里；
  2. **链到它的地方**（索引、别的文档里的引用）清干净；
  3. 编号**永不复用**。

⚠️ 无论哪种情况，都不要为同一个主题再写一份新 Spec——新方案的细节写进 ADR 和架构文档就够了。
⚠️ 决策记录（ADR）永不删除：被替代的 ADR 标 `Superseded` 永久留存。

只有**功能本身变了**（做什么、做到什么算完成），才回头改 Spec 正文。

改完之后，花十秒查三个地方有没有旧内容残留：架构文档、文档索引、进度文档。

用户已经拍板的删除或移除：直接执行，不用再反复确认——照旧先搬验收标准、清引用、编号不复用。

**改完代码后的收尾**：代码改动让哪份文档的说法过时了，就更新哪份。
例：模块目录从 src/http/ 挪到了 src/modules/ → 架构文档里的旧路径要改；没提到它的文档不用动。
分寸：事实清楚的过期描述（功能已删、命令已移除、路径已变）直接修文档，不用问；只有分不清"该改代码还是该改文档"（两边意图打架）时，才停下来问。

## 红线（每条都是硬的）

- 一个主题只留一份"现在算数"的文档。
- 仓库已有约定 > 本技能的默认。
- 什么时候才建 Spec：动到用户看得见的行为、跨多个模块、动接口/数据/安全、验收标准一句话说不清。
  例：换数据库要建；修按钮错位、改文案、私有函数改名，不用建。
- 没真实验证过，不标 `Completed`；没确认是现行方案，不标 `Active` / `Accepted`。
- 代码和文档打架，还牵扯范围、数据、安全或对外接口：停下来问，别自行挑边。
- 密钥、Token、个人隐私、完整生产日志：一个字都不进文档。
- 用户没授权，不删、不归档、不改名、不批量重组文档。
- 没跑过的测试，别说跑过了。
- 没依据的数字、日期、路径、状态：宁可写"待确认"，不许编。
- 写出来的东西要能照着做、照着验。
  反例："确保性能可接受"；正例："接口 P95 < 200ms（用 test/api-benchmark.ts 实测）"。

## 细则一：治理原则

- 一类文档只干一件事。怎么分：产品文档说"为什么做、为谁做、做什么"；架构文档说"系统整体怎么搭"；Spec 说"这个功能怎么做、怎么验收"；决策记录说"当时为什么选这个方案"；进度说"现在做到哪"；运维说"怎么部署、怎么救"。
  反例：把产品规划、代码细节、排错过程、每日进度堆进同一个文件。
- 文档是长期资产，不是写一次就扔的材料：行为、接口、数据、决策变了，受影响的文档跟着代码一起更新。
- 代码说事实，文档讲意图。两边对不上时，先判断谁错了：
  - 代码跑偏了（和确认过的需求不一致）→ 修代码；
  - 原方案行不通 → 先改设计或决策，再留实现；
  - 分不清谁对 → 停下来确认，不许闷声挑一边。
- 文档数量跟着项目复杂度走，不是越多越好。小项目几个核心文件就够。
- 留有价值的历史（重要决策、迁移说明、指导过重要版本的 Spec），不留过程垃圾（临时命令输出、排错流水、无结论草稿）。
- 内容要具体可验，每条约束至少带一样可靠依据（具体数值、文件路径、函数名、命令或检查方法）：
  反例："功能行为符合产品文档" → 正例："对照验收清单逐条在真机操作确认通过"；
  反例："允许有限次数重载" → 正例："最多自动重载 2 次，24 小时内超 2 次停止并记日志"；
  反例："1. 安全和行为边界；2. 宠物固定人格；3. 用户基础资料。" → 正例："1. 安全边界（告诉模型不能执行终端命令、不能访问文件系统）；2. 宠物人格（定义角色名字、性格和表达方式）；3. 用户资料（从 profile 记忆里取：称呼、职业、偏好）。"
  规则：列概念时，每个都要说清"里面装了什么"和"和相邻概念差在哪"；说不清的两个概念应该合并。

## 细则二：结构与类型

- 标准目录（示意图，仓库已有自己的结构就照它的来）：

  docs/
  ├── README.md        # 文档索引：列当前有效文档和阅读顺序
  ├── product/         # 产品文档：定位、用户、范围、路线图
  ├── architecture/    # 架构文档：模块、接口、数据、部署、安全
  ├── specs/           # 功能 Spec：一个功能一份
  ├── decisions/       # 决策记录（ADR）：一个决策一份
  ├── progress/        # 阶段进度
  ├── operations/      # 运维文档：配置、部署、备份、故障
  └── archive/         # 归档

  小项目不用硬凑齐：product.md + architecture.md + specs/ + progress.md 起步，长胖了再拆。

- 文档类型总表：

  | 类型 | 放哪 | 活多久 | 主要内容 |
  |------|------|--------|----------|
  | 项目入口 | 根目录、docs/README.md | 长期维护 | 项目介绍、文档索引、阅读顺序 |
  | 产品文档 | docs/product/ | 长期维护 | 定位、用户、范围、优先级、路线图 |
  | 架构文档 | docs/architecture/ | 长期维护 | 模块、接口、数据、部署、安全边界 |
  | 功能 Spec | docs/specs/ | 功能全生命周期 | 单项功能的需求、方案、任务、验收 |
  | 决策记录 | docs/decisions/ | 永久保留 | 重要选择、替代方案、收益与代价 |
  | 阶段进度 | docs/progress/ | 阶段内维护 | 已完成、进行中、下一步、阻塞项 |
  | 运维文档 | docs/operations/ | 长期维护 | 配置、部署、监控、备份、恢复 |
  | 归档文档 | docs/archive/ | 只读保留 | 已被替代但仍有历史价值的内容 |

- 根目录四件套（按需）：README.md（项目介绍和常用命令）；AGENTS.md（AI 工具的仓库规则，可选）；CONTRIBUTING.md（协作规范，可选）；CHANGELOG.md（对外的版本变化，可选）。
- 运维文档该写哪六样（有部署或长期运行需求时）：环境变量和配置来源；部署、升级和回滚；数据备份与恢复；日志和监控入口；常见故障及安全处理；密钥管理原则（写原则，不写真实密钥）。
- 建文档的时机：不预建空文件；需求真出现了才建；同主题已有文档就更新它，别重复建；研究性内容形成结论了才转正。
- Spec 的粒度：一个 Spec 管一个能独立开发和验收的功能。
  例：用户登录、文件上传、数据迁移，各一个 Spec；"做完整个系统"不拆成 Spec，纯样式调整不配 Spec。
- 什么时候写 ADR：选框架、定模块划分、增删关键依赖、改数据模型/部署/安全边界、多方案取舍。
  ADR 永不删除，被替代就标 `Superseded` 链到新决策。
- 架构文档只写"当前算数"的方案。被换掉的方案去 ADR 或 Git 历史里找，别在正文里摆两套打架的方案。
- 进度文档只记四样：已完成、进行中、下一步、阻塞项。不是流水账。

## 细则三：命名与状态

- 文件名小写英文加短横线。别用 new、final、latest、"最终版"；要翻旧版去 Git 历史，别复制文件。
  反例："接口设计最新版-v3.md"；正例："api-design.md"。
- Spec 和 ADR 各自三位递增编号（001-、002-…）。编号只表示创建顺序，废弃后永不复用。
- 元信息至少四件套：状态 / 创建日期 / 最后更新 / 关联模块；团队协作再加负责人和关联里程碑。
- 状态含义速查：
  - `Draft` 讨论中，不能当实施依据；
  - `Approved` 定了，可以开工；
  - `In Progress` 干着；
  - `Completed` 做完且验收过；
  - `Blocked` 卡住了；
  - `Active` 一直有效、长期维护；
  - `Deprecated` 内容过时，暂留；
  - `Superseded` 被别的文档或决策明确替代；
  - `Archived` 归档不再维护。
  ADR 专用：`Proposed`（待确认）/ `Accepted`（已采纳）/ `Rejected`（没采纳）/ `Superseded`。

## 细则四：生命周期与冲突

### 什么时候建 Spec（满足任何一条就建）

改了用户看得见的行为；跨多个模块/服务/进程；动 API、协议、数据表或迁移；有安全/权限/数据风险；预计干超过半天；需要多人或 Agent 连续多步；完成标准一句话说不清。
不用建的：改文案、调样式（行为没变）、修明摆着的 bug——但要有清楚的任务描述和验证结果。

### Spec 的一生

`Draft` → `Approved` → `In Progress` → `Completed`。
半路出状况：卡住标 `Blocked`；开工前作废标 `Deprecated`；做完后被替代标 `Superseded`。
干活时：实现和 Spec 有合理偏差，及时写回去；方案大变，先改决策或架构文档；没验证过，别标完成。

### 方案演进/替代时的处置（和主文件"改文档"两问同一套规则）

- 第一问定状态词：整个方案被换 → `Superseded`；只是做法变了 → `Deprecated`。都要写新 ADR 讲清为什么，两边互留链接。
- 第二问定删留：旧方案还在跑（过渡、回滚、迁移）→ 留着标状态，下线后再删；已经没人用 → 建议删（删前搬验收标准、清引用、编号不复用；硬要留，状态和链接必须维护好）。
- ADR 永不删。只有功能范围或验收标准本身变了，才回改 Spec 正文。

### 什么变化必须更新文档

产品范围/用户流程/对外行为变了；API 或消息结构变了；数据表或迁移变了；模块职责和依赖方向变了；安全策略变了；配置/部署/备份/恢复流程变了；原来的验收标准不适用了；重要决策被替代了。
通常不用更新：私有重命名、不改行为的内部重构、格式化注释、测试内部调整、没长期价值的排错过程。

### 更新文档时查哪些地方（完整顺序）

目标功能 Spec → 架构文档 → 产品文档 → 决策记录 → 阶段进度 → README/运维/Agent 规则。不是每次都全改，只改真受影响的；其中架构、索引、进度三处最容易漏（主文件要求的最小检查集），改动碰到产品行为或部署运维时，产品文档和运维文档也要进清单。文档更新和代码改动同一批提交，别留"代码新文档旧"的尾巴。

### 对不上时以谁为准

- 产品做不做 → 看 `Active` 的产品文档；
- 系统现在怎么跑 → 看代码和 `Active` 的架构文档；
- 这个功能怎么验收 → 看 `Approved`/`In Progress` 的 Spec；
- 当初为什么这么选 → 看 `Accepted` 的 ADR；
- 做到哪了 → 看进度文档；
- 怎么部署恢复 → 看 `Active` 的运维文档。

对不上的处理顺序：标记冲突 → 查代码/测试/决策/提交历史 → 确认真实意图 → 修过期那一方 → 必要时补 ADR → 最后只剩一个算数的结论。
牵扯数据、安全、对外接口或大范围代码的冲突，别自行假设，先问负责人。

### 归档、替代与删除

- 该留的：指导过重要版本的 Spec、长期技术选择、迁移兼容说明——标 `Superseded`/`Archived` 并指向接棒文档。
- 可以删的：空文件、没人引用的重复草稿、无结论的临时记录、已完整并进正式文档的副本。
- 删之前查一遍还有谁引用它。重要历史 Git 都留着，仓库里不要堆"备份版""旧版"文件。
- ADR 例外：永不删除。

## 细则五：AI 协作与维护

### AI 开发前先做六件事

1. 读仓库级规则；
2. 读文档索引；
3. 读相关产品范围、目标 Spec 和架构文档；
4. 查目标 Spec 的状态和非目标；
5. 查有没有相关决策记录；
6. 发现冲突或重大缺失，先报告，别自己补关键决策。

推荐阅读顺序：仓库规则 → docs/README.md → 产品范围 → 当前进度 → 目标 Spec → 相关架构 → 相关决策和运维。
上下文有限时优先读：目标 Spec、相关架构、当前范围、安全约束。

### AI 干活时别做的事

没确认就改产品定位和阶段范围；同时建多份重复方案文档；拿新文件顶替有效文档还不说明关系；发现代码文档不一致闷声挑一边；顺手实现范围外的问题；往文档写密钥和敏感数据。

### 干完活要做的事

按验收标准真跑一遍验证；分清"验证过""没验证""验证不了"；更新 Spec 状态和实施结果；更新受影响的架构/运维文档；更新进度；没跑过的测试不说跑过。

### 评审一份文档看什么

目标和范围清楚；有非目标；术语统一；没有两套打架的现行方案；验收标准能观察能验证；关键约束带具体数值/路径/方法；链接指向有效文档；没有敏感信息；和当前代码一致。
反例："确保性能可接受""保持代码整洁"——没法判断的表述都不合格。

### 维护节奏

每次功能开发前：确认或建 Spec、检查产品范围、读相关架构和决策。
每次功能完成后：更新 Spec 状态和结果、更新进度、查架构/运维是否受影响、删无价值临时文档。
每个里程碑：检查 `In Progress`/`Blocked` 是否真实、清理过期草稿、核对产品架构代码有没有大偏差。
每次发布前：确认发布范围内 Spec 已验收、更新部署回滚说明、查敏感数据。
定期治理（每月或每个大版本）：查失效链接；查长期没更新的 Active 文档；查重复主题；查已被代码推翻的旧结论；查没人维护的 Draft；过长的文档合理拆分。

### 新项目落地八步（按需逐步加，别一次建全）

1. 根目录 README.md：项目目的和运行方式；
2. docs/product.md：范围、目标和非目标；
3. docs/architecture.md：初始模块和数据流；
4. docs/progress.md：当前计划和状态；
5. 第一个复杂功能 → docs/specs/001-*.md；
6. 第一个重要技术选择 → 第一份决策记录；
7. 出现部署和长期运行需求 → 运维文档；
8. 文件多了 → 建 docs/README.md 索引并拆目录。

### 做到什么样算好（完成标准）

- 新人靠 README 和索引能快速理解项目；
- 每个复杂功能有明确范围和验收标准；
- 当前架构和代码基本一致；
- 重要技术选择能追溯原因；
- 当前进度和阻塞项一眼可查；
- 旧方案不会和现行方案混淆；
- AI 能找到足够上下文，又不会被过期信息带偏；
- 文档更新是开发完成条件的一部分，不是事后补的活。

## 完工前自查

- 是出主意或评审的活：说清"我没改任何文件"。
- 是建或改文档的活：路径、命名、状态、链接、"一个主题一份有效文档"、敏感信息，逐项过一遍；Spec 还要检查有没有明确的范围、非目标、能验证的验收标准。
- 最后报告实际动了哪些文件，哪些验证过了、哪些没有。
