# 项目文档管理

## 目标

在不改变既有产品决策、仓库约定和用户授权范围的前提下，创建、更新、评审或组织软件项目文档。

## 任务入口

1. 判断任务类型：建议或规划、审核、创建、更新、代码实施后的配套文档。
2. 读取仓库级规则；若存在文档索引、产品总纲、相关 Spec、架构或决策记录，只读取与当前任务有关的内容。
3. 检查是否已有同主题文档，并确认当前有效来源。
4. 仓库规则、用户要求和当前有效文档发生冲突时，指出冲突并请求确认，不自行选择。
5. 不默认读取完整 reference。

## 按任务执行

### 建议或规划

只输出建议、清单、依赖关系或执行顺序。用户未要求创建文件时，不修改文件。

### 审核

先输出按严重程度排序的问题，并提供文件或章节定位。用户未明确要求实施时，不修改被审核文档。

### 创建

先确认没有重复或重叠文档，再选择对应 asset 作为起点。遵循仓库现有目录、编号和元信息格式；没有既有约定时才使用本 Skill 的默认规范。新文档默认使用 `Draft`，新 ADR 默认使用 `Proposed`。

### 更新

修改当前有效文档，不另建"新版""最终版"或重复文件。方案被新决策明确替代时，在获得授权后标记 `Superseded`，并建立双向链接。同主题的实施方案演进（换框架、换实现而对外行为不变）时，不回改旧 Spec 正文：新决策记入新的决策记录，旧 Spec 按「在跑标 `Deprecated`、退役即删除」处置。

更新完成后顺手检查三处——架构文档、文档索引、阶段进度，清理指向被改文档的过期引用。

用户已明确授权的删除或移除可直接执行：先转移仍然有效的验收标准，再清理所有引用与索引，编号不复用。

### 代码实施后的配套文档

只有当代码变更使现有产品、架构、接口、数据、配置、运维或验收说明失效时，才同步更新受影响文档。不要扩大到无关文档。

## 核心约束

- 一个主题只保留一个当前有效来源。
- 既有仓库约定优先于本 Skill 提供的默认目录和命名方式。
- 涉及用户行为、多模块、接口、数据、安全风险或多步骤验收时，优先创建功能 Spec；简单文案、无行为变化的样式调整和直接 Bug 修复通常不需要。
- 未经真实验证，不得标记为 `Completed`；未确认是当前有效方案，不得标记为 `Active` 或 `Accepted`。
- 代码与文档冲突且会影响范围、数据、安全或外部接口时，暂停相关扩展并请求确认。
- 不写入真实密钥、Token、个人敏感数据或完整生产日志。
- 未经明确授权，不删除、归档、重命名或批量重组文档，不安装、发布或修改外部资源。
- 不把未执行的测试或检查描述为已通过。
- 不得为了满足模板或"具体、可验证"的要求而虚构信息。缺少可靠依据时，不编造数值、日期、负责人、文件路径、接口、状态或验证结果；标记为"待确认""未提供"或"未验证"，并区分已确认事实、建议方案和待定项。
- 文档内容必须具体、可验证，并能明确指导操作或判断。发现"看起来有道理但不知道怎么做"的描述即视为不通过。

## 完成条件

建议、规划或审核任务以完成用户要求的输出为准，并明确说明未修改文件。

创建或更新任务结束前，检查目标路径、命名、元信息、状态、链接、单一有效来源和敏感信息。功能 Spec 还必须具有明确范围、非目标和可验证验收标准。

最终报告实际创建或修改的文件，并区分已验证、未验证和当前无法验证的内容。

## 参考细则一：治理原则

- 一类文档只干一件事：产品文档说"为什么做、为谁做、做什么"；架构文档说"系统整体怎么搭的"；Spec 说"这个功能怎么做、怎么验收"；决策记录说"当时为什么选这个方案"；进度说"现在做到哪"；运维说"怎么部署怎么救"。别把规划、代码细节、排错过程、进度堆进同一个文件。
- 文档是长期资产：不是开发前写一次就扔的材料，行为、接口、数据、决策变了，受影响的文档跟着代码一起更新。
- 代码说事实，文档讲意图。两边对不上时：代码跑偏了就修代码；原方案行不通就先改设计再留实现；分不清谁对就停下来确认；不许闷声挑一边继续干。
- 文档数量跟着项目复杂度走，不是越多越好。
- 留有价值的历史（重要决策、迁移说明），不留过程垃圾（临时输出、排错流水、无结论草稿）。
- 一个主题只有一份"现在算数"的文档；旧方案明确标记已被替代，并链到新方案。
- 内容要具体可验：别写"功能符合产品文档"这种空话（要写成"对照验收清单逐条在真机操作确认"）；别写"允许有限次重载"（要写"最多重载 2 次，24 小时超 2 次停止"）；别罗列光秃秃的概念名词（要说明每个概念包含什么、和相邻概念差在哪）。每条约束至少带一样可靠依据：具体数值、文件路径、函数名、命令或检查方法。

## 参考细则二：结构与类型

- 标准目录：docs/ 下分 README.md（索引）、product/、architecture/、specs/、decisions/、progress/、operations/、archive/。小项目从 product.md + architecture.md + specs/ + progress.md 起步，长胖了再拆。
- 建文档的时机：不预建一堆空文件；需求真出现了才建；同主题已有文档就更新它，别重复建；研究性内容形成结论了才转正。
- Spec：一个 Spec 管一个能独立开发和验收的功能。别建"做完整个系统"的大 Spec，也别给纯样式调整建 Spec。
- 决策记录（ADR）：选框架、定模块划分、增删关键依赖、改数据模型/部署/安全边界、多方案取舍时写。已采纳的决策后来被替代也不删——标 `Superseded` 链到新决策。
- 架构文档只写"当前算数"的方案；被换掉的方案去决策记录或 Git 历史里找，别在正文里摆两套打架的方案。
- 进度文档只记当前状态：已完成、进行中、下一步、阻塞项。不是流水账。

## 参考细则三：命名与状态

- 文件名小写英文加短横线；别用 new、final、latest、"最终版"这种词；要翻旧版去 Git，别复制文件。
- Spec 和决策记录各自三位递增编号（001-、002-…）；编号只表示创建顺序，废弃后永不复用。
- 元信息：状态 / 创建日期 / 最后更新 / 关联模块。
- 状态一览：Draft 讨论中不能当依据；Approved 可以开工；In Progress 干着；Completed 做完且验收过；Blocked 卡住；Active 一直有效长期维护；Deprecated 不再推荐但暂留；Superseded 被别的文档替代；Archived 归档。决策记录用 Proposed / Accepted / Rejected / Superseded。

## 参考细则四：生命周期与冲突

### 什么时候该建 Spec（满足任何一条就建）
改了用户看得见的行为；跨多个模块/服务/进程；动 API、协议、数据表或迁移；有安全/权限/数据风险；预计干超过半天；需要多人或 Agent 连续多步；完成标准一句话说不清。改文案、调样式、修明摆着的 bug 不用建，但要有清楚的任务描述和验证结果。

### 生命周期
Draft → Approved → In Progress → Completed；半路出状况：In Progress 卡住标 Blocked、Approved 作废标 Deprecated、Completed 被替代标 Superseded。干的过程中：实现和 Spec 有合理偏差就及时写回去；方案大变先改决策或架构；没验证过别标完成。

### Completed Spec 的方案演进
适用于"换框架、换架构、换实现，但对外行为没变"的演进。整个方案被新决策明确换掉的情况不适用本节——那走 Superseded + 双向链接。演进时别回改正文重写历史：
1. 为什么换、新方案要点，写进一篇新的决策记录；
2. 旧 Spec 还在跑（灰度、新旧并存、要留回滚窗口）：标 `Deprecated` 并链接新决策，等旧方案彻底下线后再删；
3. 旧方案已经彻底退了：直接删旧 Spec——先把还管用的验收标准搬到新 Spec 或测试，再清掉所有指向它的链接和索引，编号不复用；
4. 只有功能范围或验收标准本身变了，才回改 Spec 正文。

### 什么变化必须更新文档
产品范围/用户流程/对外行为、API 或消息结构、数据表或迁移、模块职责和依赖方向、安全策略、配置部署备份恢复流程、验收标准失效、重要决策被替代。
什么变化通常不用更新：私有重命名、不改行为的内部重构、格式化注释、测试内部调整、没有长期价值的排错过程。

### 更新查三处
架构文档、文档索引、进度文档。不是每次都全改，只改真受影响的；文档更新和代码改动同一批提交，别留"代码新文档旧"的尾巴。

### 信息以谁为准
产品做不做看 Active 产品文档；系统怎么跑看代码和 Active 架构；怎么验收看 Approved/In Progress 的 Spec；为什么选某方案看 Accepted 决策；做到哪了看进度；怎么部署看 Active 运维。对不上时：标记冲突 → 查代码/测试/决策/提交历史 → 确认真实意图 → 修过期那一方 → 必要时补决策记录 → 最后只剩一个算数的结论。牵扯数据、安全、对外接口或大范围代码的冲突别自行假设，先问负责人。

### 归档、替代与删除
该留的：指导过重要版本的 Spec、长期技术选择、迁移兼容说明——标 Superseded/Archived 并指向接棒文档。可以删的：空文件、没人引用的重复草稿、无结论的临时记录、已完整并进正式文档的副本。删之前查一遍还有谁引用它。重要历史 Git 都留着，不要在仓库里堆"备份版""旧版"文件。

## 参考细则五：AI 协作与维护

### AI 干活时别做的事
没确认就改产品定位和阶段范围；同时建多份重复方案文档；拿新文件顶替有效文档还不说明关系；发现代码文档不一致闷声挑一边；顺手实现范围外的问题；往文档写密钥和敏感数据。

### 干完活要做的事
按验收标准真跑一遍验证；分清"验证过""没验证""验证不了"；更新 Spec 状态和实施结果；更新受影响的架构/运维文档；更新进度；没跑过的测试不说跑过。

### 评审一份文档看什么
目标和范围清楚；有非目标；术语统一；没有两套打架的现行方案；验收标准能观察能验证；关键约束带具体数值/路径/方法（"确保性能可接受"这种不合格）；链接指向有效文档；没有敏感信息；和当前代码一致。
