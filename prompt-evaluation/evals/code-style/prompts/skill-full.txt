# 代码风格规范

统一的个人代码风格约定。目标是让代码按逻辑分段、注释说明"为什么"，并在不过度抽象的前提下易于维护和扩展。

> 本文中的原则与约束属于规范；代码仅用于说明。标识符、目录名、配置键和示例数值应结合当前项目调整，除非正文明确标注为固定要求。

## 适用优先级

按以下顺序应用规则：

1. 用户对当前任务的明确要求；
2. 仓库级规则、格式化工具、Lint 配置和目标文件已形成的局部惯例；
3. 本 Skill 的默认约定。

只调整当前任务涉及的代码。不要为了统一风格批量改写无关文件、既有注释或稳定接口；现有写法不违反更高优先级规则且不妨碍维护时，保持不变。

## 核心规则（含参考细则，已全部加载）

### 1. 注释

- 优先遵循仓库已有的注释语言；没有约定时默认使用中文。不要仅为统一语言批量翻译既有注释。
- 仅在文件或模块职责无法从名称和结构直接判断时，使用适合当前语言的块级注释说明整体职责。
- 当英文术语、语言特有语法或类型声明明显增加目标维护者的理解成本时，可用一句中文说明用途；不要逐行翻译代码或把注释写成语法教程。
- 无需逐行注释；显而易见的代码不加注释。
- JSON（`package.json` 等）不支持注释，不要写入。
- 需要整体说明的重要常量或数据表（如状态码表、注册表、枚举映射），在变量上方使用块级或文档注释统一说明；可用箭头 `→` 表示映射关系，或用 `1. 2. 3.` 序号列举各项。
- 流程类说明用箭头串起步骤，步骤类说明用序号列举。
- 注释解释"为什么"（安全边界、防漂移、性能、兼容原因），不只复述代码在做什么；为关键函数/导出项标注职责与约定。
- 在 JavaScript 或 TypeScript 中，仅为契约、边界、副作用或使用方式无法从名称和类型直接判断的公共导出项使用 JSDoc（`/** */`）；需要时用 `@param`、`@returns` 等标签补充类型系统没有表达的信息。不要为每个导出项机械添加重复类型定义的注释。

### 2. 空行

- 按逻辑步骤分段，段间加空行，避免大段代码挤在一起。
- 一段代码只做一件事；不要把"解析 → 校验 → 组装 → 返回"压成连续一行。
- 入口文件优先展示"准备 → 执行 → 输出"的主流程；复杂细节使用含义明确的函数封装，但不要为简单代码过度拆分。

### 3. 按关注点拆分

- 避免在一个块里平铺大量跨越多个关注点的属性；规模较小、职责单一且总是整体消费的配置可以保持在一起。
- 当配置包含多个独立关注点、不同部分会分别变化或被不同消费方使用时，按关注点拆成内聚切片；消费方按需引入，组合由入口或调用方完成。
- 根据职责、变化原因和消费方拆分切片，不以字段数量作为硬性标准；不要为了拆分而制造大量只转发一两个值的文件。
- 只有被多个切片实际复用，或已形成稳定边界时，才把基础逻辑提取到 `common` 类模块。
- 需要稳定统一入口时，可由 `index.js` 等入口文件汇总重导出。

### 4. 简化条件逻辑

- 不写降低可读性的多层嵌套三元。
- 优先选择当前场景中最直接的表达：提前返回、清晰的 `if` / `else`、`switch`、映射表或注册表均可。
- 当条件由稳定键映射到数据、选项会持续扩展且各分支结构一致时，使用注册表 + 查表函数。
- 只有两三个简单分支，或每个分支包含明显不同的行为时，不要为了使用注册表而增加间接层。
- 使用注册表时，错误提示可基于注册表动态生成，避免另行维护重复的枚举列表。

### 5. 避免过度抽象

- 公共包只保留多个消费方已经共享，或属于明确稳定边界的部分（常量、契约、动作名）。
- 单侧使用的状态码、错误处理、类型守卫等实现细节留在所在模块，不要塞进公共包。
- 抽取共享模块前先确认消费方和变化方向。只有一个消费方且没有明确边界价值时，通常不算"共享"。
- 边界尚不稳定时，允许暂时保留少量重复，等共同模式明确后再抽取。
- 抽取后保持"共享面"最小，只暴露消费方真正需要的部分。

## 验证

- 修改后运行仓库现有测试命令（如 `pnpm test` / `npm test`）。
- 同时运行仓库已有的格式化、Lint 或类型检查命令；不存在时不额外引入工具。
- 交付前复核注释、空行、条件表达与模块边界，并确认没有无关的风格改写。
