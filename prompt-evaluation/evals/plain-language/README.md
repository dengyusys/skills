# plain-language：去 AI 味·说人话（文档改写提示词）

## 测什么

把"读起来费劲"的 markdown 文档改写成说人话版本的提示词对比。6 个案例全部固化自 `D:\ui-library` 的 markdown 摘录（design-language.md 五段、animation-methodology.md 一段），覆盖五类典型"AI 味"写法：箭头链当句子、斜杠并列堆砌、自创压缩词不解释、括号套括号一句塞三事、满篇加粗/等号当动词。

## 与 code-reading 的关系（合并实验后的结论）

code-reading 的初衷本来就是两件事：读代码讲明白 + 输出别有 AI 味。2026-09-12 的合并实验证明两条线是同一目标的两面：

- v6 的输出样式是 AI 味重灾区（6 篇合计 112 处加粗、36 处"——"），挂上表达卫生预算后 v7（v6 + 表达卫生）在 code-reading 考卷 6/6 内容样式双过；
- 合一分支版提示词（v4）在本考卷 5/6，与专家版 v3 持平；但它的代码分支（v6 蒸馏版）在 code-reading 考卷只有 4/6——规则一压缩就丢细节。

**最终架构：技能合一（公共表达卫生 + 两个完整任务分支），考卷分开（本测评与 code-reading 各测各的分支，黄金集各自冻结）。** 合并提案见 [../PROPOSAL.md](../PROPOSAL.md)。

（本测评最初以"任务性质不同"为由独立成目录；经实验修正为上述结论——考卷仍然分开，理由只剩"黄金集不可混"一条，但这条依然成立。）

## 机械断言（本测评新增两条，已进 core/）

| 断言 | 抓什么 |
|------|------|
| `marker_density_reduced.py` | 加粗/破折号/箭头三类标记，改写后不得比原文更密；原文总量 ≥4 时必须下降（代码块与行内代码内的记号不计） |
| `code_facts_preserved.py` | 原文的行内代码、代码块、链接 URL 必须逐字保留——去 AI 味只改表达，丢技术记号即失败 |
| `no_prose_wall.py`（复用） | 防止把列表腔改成大段文字墙 |
| `layout_breathing.py` | 版式呼吸五项预算：段落 ≤150 字、列表项 ≤120 字、表格格 ≤45 字、表格字符占比 ≤50%（400 字起算）、连续列表 ≤8 项（代码块不计） |

另有两条通用裁判断言（在 eval.yaml 的 defaultAsserts）：改写后像人写给同事的说明；没有改出新的 AI 味（骨架词、总结段）。

### 约束量实验（R10-R12：极简版 + 强模型探针 ×2）

用户假设："约束太多，模型更好时反而有负影响。"为此做了 v8 极简版（约束约 1/4、去掉全部示例）并把被测模型临时换成更强的 glm-5.3（裁判不变；providers.yaml 改后已还原，共跑两轮）。

| 变体 | flash 三轮（文档面） | glm-5.3 两轮（文档面） | flash（代码面） | glm-5.3 两轮（代码面） |
|------|:---:|:---:|:---:|:---:|
| v6 合一+版式（文档面最高分） | 4/4/3 | 3/2 | - | - |
| v7 完整分支 | 2/2/2 | **4/4** | 6/6（v9 同文本） | 3/3 |
| **v8/v9b 极简** | 1/2 | 1/1 | 4/2 | 4/4 |
| （对照）v7 专家版（代码面最高分） | - | - | 6/6/6 | 5/5 |
| （对照）v8-unified 蒸馏合一 | - | - | 4/4/5 | 4/4 |

结论：

1. **"约束多伤好模型"只对了一半**。完整版在弱模型上有稀释代价（v7 文档面 2/6），换强模型后代价消失（4/4）——好模型吃得下重规则；但极简版在强模型上仍是 1/6，没有反超。失败清一色是预算不遵守（加粗、破折号、段落长度）：这些是模型默认不做的事，规则不是"纠正它想做的"，而是"要求它做它不会自发做的"——这类约束不可省。
2. **最高分提示词在强模型上基本无负影响**：文档面 v6 持平（3-4 → 2-3，摇摆带内）；代码面专家版 v7 稳定 5/5，比 flash 的 6/6 少的那一题两轮相同（record-updater：强模型把 structuredClone 深拷贝意译成"拷贝一份"，没点名机制）——是转述习惯撞上裁判口径，不是能力被约束束缚。
3. **真实的负影响出现在"超长合一文本"上**：v9（flash 上 6/6 的并列最高分）在强模型两轮都稳定 3/6，且挂的是同样三题（防抖闭包存续、Dockerfile 结构化、record-updater 阅读地图）。与弱模型被 v7-full 长文本稀释（文档 2/6）对称：**合一文本越长，两个模型都各有各的稀释**，"模型越强越能吃长提示词"不成立；专家版 v7 在两个模型上最稳（6/6 与 5/5）。
4. **可省的只有"怎么拆"示例**（教弱模型的教具）；对强模型它们暂时没测出害处，也没测出收益。
5. 台账备注：强模型四轮（13:55、14:03 及第二轮两次）的 model 字段记为 glm-5.3-flash，实际被测是 glm-5.3（run.cjs 硬编码，以本节为准）；13:49/14:03 的 code-reading 变体标签因文件排序错位一格（v10-minimal 排在 v1 与 v2 之间），已改名 v9b-minimal 修复，错位两轮的实际成绩以本表为准。

### 用户原则版补测（v9 / v9c，两个模型各一轮）

用户自写的原则式版本（先理解再表达 / 像懂的人在解释 / 控制阅读负担，无数字预算、无示例）：

| 面 | flash | glm-5.3 强模型 | 同轮对照 |
|------|:---:|:---:|------|
| 文档（v9） | 1/6 | 1/6 | v6 3-4 / 07 强模型 3 |
| 代码（v9c） | 3/6 | **0/6** | v7 6（flash）/ 5（强） |

失败高度可归因——**恰好是文本里没提到的标记在失控**：

- **加粗完全没提** → 强模型每篇稳定加粗 10 处（预算 8），多篇因此挂；flash 文档面 1→11。
- **破折号没提** → 强模型 3-5 处（预算 2）。
- **示意图反传染条款缺失** → 闭包题照抄了材料里的 Unicode 制表符（"简单 ASCII 字符"挡不住材料传染，必须显式写"不得照抄材料的画法"）。
- 反过来，**它写到的都做到了**：箭头/斜杠/等号基本受控；强模型在 Apple 题的术语解释被裁判点名表扬；"策略更新仅在有反馈时生成"的设计优于 v7 的每次必输出。

结论：原则式写法的骨相是好的，但再次验证同一条规律——**没写出来的维度，模型（包括强模型）会退回自己的默认习惯，而强模型的默认习惯更稳定（每篇恰好 10 处加粗）**。这版距离可用差三行：加粗与破折号的上限、示意图禁抄材料画法；要不要补数字预算是取舍（补了稳定，不补就接受版式摆动）。

### 用户终版记录（v10 / v9d，2026-09-13，R15 理解考卷）

用户迭代出的最终形态：七条核心原则（先理解再表达 / 说人话 / **不改事实（技术信息逐类列全）** / 自然组织 / 控制解释深度 / 保持上下文一致 / 不要过度改写）+ 按任务类型处理 + 输出规范；相对原则版吸收了本轮实验的三个发现（记号清单、术语一致性、勿过度改写），并删除了代码分支的全部专属规则。

| 面 | flash | glm-5.3 强模型 | 同轮对照（原则版 → 终版） |
|------|:---:|:---:|------|
| 文档（v10） | 3/6 | **5/6** | 强模型 1 → 5 |
| 代码（v9d） | 4/6 | 2/6 | 强模型（体验尺）5 → 2 |

- **文档面高光**：强模型 5/6，全卷只丢一个记号（`animation-delay:`）——"不改事实"清单明确起效。flash 3/6 的失败：提案卡丢 4 个记号（执行波动）、输出自加「# 改写版」标题、Apple 三原则仍只有直译。
- **代码面回落**：终版删掉了"先比方后术语"的顺序规则和示意图 ASCII 规则，代码考卷恰好考这两样——强模型挂在防抖（术语先于类比、闭包存续没讲）、write-queue（没先用日常事理铺垫）、executor（顺手小事没讲为什么）、record-updater（照抄了材料的 Unicode 画法，撞 v1 以来的 ASCII 老规则）。
- **定位**：作为通用"说人话"提示词（文档改写为主）已经好用；用于代码讲解不如保留那两条规则的上一版或 v7。

### 用户终版二记录（v11 / v9e，2026-09-13）

用户在终版基础上吸收 R16 两题的修法：「不改事实」加"讲解代码时不修改/重排/补注释，说明写在代码之外"；新增「最小充分解释」一节（一句话能讲清就不扩展）。

| 面 | flash | glm-5.3 强模型 |
|------|:---:|:---:|
| 文档（8 题） | 4/8 | 5/8 |
| 代码（6 题） | 3/6 | 4/6（终版一为 2/6，改善） |

两个靶向修复均起效但未收口：

- **07 闭包题**：挂因从"往代码里插注释"退化为"删了代码里的空行"——讲解已全部移到代码外，注释一条没插；剩的是空白格式洁癖（两模型一致）。修法：规则里补"包括空行和缩进在内一字不改"。
- **08 克制题**：答案长度砍半（628→358 字 flash、488 强模型）但仍为预算（120 字）的 3 倍，且仍给运算符下定义、与 || 对比。"最小充分解释"方向对、力度未到。

### 标尺修订（R13，用户裁定：绝对预算降为观察项）

用户对上节结论提出异议：加粗/破折号/版式数字超标**不应作为判死原因**——它们不是决定性因素，为满足它们加规则反而是加重约束。用已有输出离线重判（免跑模型）做了裁决：

| 变体 | 文档面 flash：现行尺 → 纯体验尺 | 文档面强模型 | 代码面 flash | 代码面强模型 |
|------|:---:|:---:|:---:|:---:|
| v9 用户原则版 | 1 → 4 | 1 → 4 | 3 → 5 | 0 → 5 |
| v8 极简版 | 2 → 6 | 1 → 5 | 3 → 3 | 4 → 5 |
| v6 合一+版式 | 4 → 5 | 3 → 5 | - | - |
| v7 专家版（代码） | - | - | 6 → 6 | 5 → 6 |

**裁决：用户观点成立。**绝对预算判死贡献了低约束版几乎全部的失败；豁免后它们落到中游，剩余失败全是内容级（丢技术记号、Apple 单元格罗列、write-queue 事理顺序）。连"极简版不行"都是旧尺的产物（纯体验尺下文档面 6/6）。

**已执行**：`layout_breathing`（plain-language）与 `prose_marker_budget`（code-reading）从 defaultAsserts 判死位移到注释里（随时取消注释恢复）；core/assertions 的脚本保留，可离线审计。**保留判死**的都是用户自定义过的硬约束：ASCII 示意图（code-reading v1 起就有）、技术事实保全、不比原文更密（相对规则）、不成文字墙。

**新格局（R13，flash 单轮，裁判摇摆 ±2）**：文档面 v6 5/6 居首，v2/v3/v4/v7/v8 4/6，用户原则版 2-4/6（同输出离线判 4，摇摆带）；代码面 v5/v6/v7/v9 6/6，**v1 陪读体复活到 5/6**（旧尺的样式判死曾把它压到 0-1——它内容一直是对的），用户原则版 5/6。冠军在两把尺子下都是冠军，标尺修订没有翻案，只是放行了中游。

**代价（如实记录）**：版式密度从此没有判死保障，"呼吸感"只剩裁判定性（Apple 表格罗列仍会被抓）与文字墙断言兜底。将来若发现输出密度回潮，取消 eval.yaml 里两行注释即可恢复预算判死。

## 关键发现

1. **朴素指令会越改越 AI**：v1 稳定 1/6，机械断言抓到加粗翻倍（1 变 13）、破折号新增，裁判抓到自加的「主要改动：…」总结段和开场设问。模型默认的"润色"就是加重 AI 味。
2. **提示词示例会被模仿，包括坏示例**：R1 的 v2/v3 输出大量出现"——"，源头是我第一版「改后」示例自己用了破折号——材料传染的教训在自己身上应验。改前/改后示例本身要过一遍自己立的规矩，并显式声明"反面教材一个都不要出现"。
3. **交稿前自查是性价比最高的一块**：技术记号保全（`.done` 的点号、`animation-delay`）和缩写解释（VT/rAF）主要靠 v3 的自查清单抓回，R2 案例 01 只有 v3 通过。
4. **解释黑话要防「用行话解释行话」**：模型爱拿「语义层」「槽位」解释「三页一制」，规则要写明"解释只许用日常词，解释不出来就换说法"。
5. **表格改写是当前硬骨头**（案例 05，v2/v3 均不稳定）：「表格不拆散」和「一格只说一件事」存在张力，模型不肯把塞满的表格降为概览表 + 表后分节。v4 方向：格内条目 ≥3 条时强制表格只留一句话概览、细节下移分节，配一个改前/改后整表示例。
6. **已知噪音**：思考文本泄漏（R2 有 4/18 输出带 "Thinking:" 前缀，core/README 已记录的基建问题，影响裁判输入）；临界案例裁判摇摆（案例 01 在 R2–R4 间因丢一个记号或多一个破折号翻转，看模式不看单点）。
7. **合一不掉分、压缩会掉分**（R5 合并实验）：合一分支版（v4）在本考卷 5/6 与专家版持平；但同一文本在 code-reading 考卷上，代码分支若是 v6 蒸馏版则 4/6（丢闭包持久化、structuredClone 两处细节）。技能合并时两个分支都必须保留完整规则，见 [../PROPOSAL.md](../PROPOSAL.md)。
8. **版式是第三个盲区**（R6-R7）：表达卫生管句子（箭头/加粗/黑话），版式呼吸管版面（密度/表格压迫）。实测此前所有最优变体都是密集型——v4 输出表格字符占比最高 74%、v3 列表项最长 222 字、code-reading v7 表格占比 55%。"表达优先使用表格和列表"这类旧规则防文字墙有效，但推过头就是表格墙。
9. **数字预算 + 拆法示例才管用**（R6→R7）：只给预算数字（R6），模型内容写得对但总是顶爆 1-2 项；补上"怎么拆"的具体示例（列表项拆缩进子项、表格格只写关键词短语、引用块拆短）后 v6 从 2/6 升到 4/6——又一次验证"具体示例胜过抽象规则"。
10. **案例 05（Apple 三原则表）至今未破**：模型系统性地不肯给表格瘦身（格内仍塞 3 件事、占比 50%+），即使规则和示例都给了，所有轮次所有变体全灭。这是当前最有价值的失败样本，v8 方向：给一张完整的"胖表 → 概览表+细节下移"改前改后对照，而不只是文字描述。
11. **合一文本的代价有了实测数字**（R8-R9）：完整代码分支塞进合一文本后，代码面满血（v9 6/6，与专家版 v7 打平），文档面却连续两轮比 v6 低约两分（2/6 vs 4/6）——提示词越长，文档分支的预算遵守越被稀释。蒸馏合一（v8 代码面 4/6）与全文合一（v7 文档面 2/6）各伤一面：**一个文本扛全部规则不成立**。技能落地形态应为 document-management 同款：主文件放公共核心与路由，分支细则放 references/ 按需加载。
12. **预算之间存在内耗**（R9 新失败模式）：性能案例把长列表项拆成 13 个短项，单项合规了，连续列表预算（≤8）爆了。两条规则字面都对、合起来打架，提示词需要"拆完按小主题分组"的显式引导（已有但被忽略），暂无低成本修法。
